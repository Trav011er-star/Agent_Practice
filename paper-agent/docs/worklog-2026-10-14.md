## 2. 实验：先看清 `.stream()` 到底吐什么

写了个一次性脚本（**跑完即删，不入库**），挑一道**跨论文、要跳 3 轮**的题——单跳的题只会吐两次，看不出"推进"。

结果 **7 帧**：

```text
[1] collect  {'items':<3>, 'seen':<3>, 'hops':1, 'tried':<1>, 'citations':<3>, 'weak_rounds':0}
[2] judge    {'enough':False, 'query':'BERT masked language model pretraining objective'}
[3] collect  {'items':<9>, 'seen':<9>, 'hops':2, 'tried':<2>, 'citations':<9>, 'weak_rounds':0}
[4] judge    {'enough':False, 'query':'GPT-3 autoregressive language modeling ...'}
[5] collect  {'items':<18>,'seen':<18>,'hops':3, 'tried':<3>, 'citations':<18>,'weak_rounds':0}
[6] judge    {'enough':True,  'query':'BERT 和 GPT-3 的预训练目标有什么不同？'}
[7] done     {'answer':'根据资料，BERT 与 GPT-3 的预训练目标不同如下：…'}
```

### 2.1 形状：一帧 = 一个节点

```python
{ 节点名字 : 这个节点 return 的那个 dict }
```

所以消费的写法是 `for node, update in chunk.items()`：
**`update` 不是别的东西，就是那个节点 `return` 出来的 dict 本身。**

### 2.2 ⭐ 一个必须想清楚的发现：`citations` 是全量，不是增量

看第 3 列：`citations` 是 **3 → 9 → 18**，而 `hops` 是 **1 → 2 → 3**。

**这两个不是一回事：**

| 字段 | 给的是 | 因为 `node_collect` 里写的是 |
|---|---|---|
| `hops` / `weak_rounds` | **绝对值** | `"hops": n` |
| `citations` / `items` / `seen` | **全量列表** | `state["citations"] + citation` |

节点返回的是"**合并后的结果**"，不是"差分"。第 2 轮那帧里，前 3 条引用**又原封不动重发了一遍**。

于是 SSE 协议有两条路：

```text
路 A：每帧发全量 citations（前端直接替换）
路 B：生成器里记 last_len，只发新增的几条
```

**选路 A，理由不是省事，是正确性**：

> **SSE 是单向广播，没有重发机制。掉一帧就是永久丢了。**
> 走 B 的话，客户端少收一帧，那几条引用**再也补不回来**；
> 走 A 的话，下一帧自带纠错。**多传几个字节，换"丢了也能自愈"，值。**

代价是前端必须**替换**而不是**追加** —— 追加会变成 3+9+18 = 30 条重复。

## 3. ⭐ 打脸：`print` 能看到的东西 ≠ stream 能拿到的东西

我第一版协议里写了：

```json
{"type":"progress", "round":1, "hits":3, "top_score":2.30}
```

**`top_score` 从哪来？** 去 `node_collect` 的 `return` 里找 —— **没有。**

```python
# node_collect 真正 return 的
{"items", "seen", "hops", "tried", "citations", "weak_rounds"}    # ← 没有 top_score
```

它只出现在这两行：

```python
top_score = fresh[0].metadata.get("rerank_score")   # ← 局部变量
print(f"... 最高分 {top_display}")                    # ← 只拿去打印了
```

**根因**：

```text
print  读的是函数【内部的局部变量】 —— 函数自己造、自己用、用完就扔
stream 只能拿到节点【return 出去】的东西
```

> **这和 10-13 §5.4 那个 `{None:.2f}` 是同一个病根的两面：**
>
> | | 症状 |
> |---|---|
> | 10-13 | **打印挂了** —— 观测代码把业务代码炸了 |
> | 今天 | **打印看得到、别人看不着** —— 观测数据没进数据流 |
>
> 都源于同一个模糊认识："**日志里有**"和"**数据里有**"是两回事。

**三个选项：**

| | 做法 | 代价 |
|---|---|---|
| **1（选它）** | 不要分数，用 `weak_rounds` 表达"这轮有效/无效" | 0 改动 |
| 2 | 给 `State` 加 `top_score` 字段 | 动 `graph.py` 两行 |
| 3 | `stream_mode="custom"` + `get_stream_writer()` | 多一个概念，动 `graph.py` |

**选 1。** 前端能有"第 1 轮 3 条（无效）→ 改写 → 第 2 轮 9 条 ✓"这条叙事就够了；具体是 2.30 还是 9.11 是锦上添花。而且 `graph.py` 昨天刚收尾，**不该为观感动它**。

（选项 3 是 LangGraph **专门为这件事设计的**机制——把观感数据从节点里发出去，不污染业务 state。将来真要把分数搬上屏幕再用它，它比选项 2 干净。）

## 4. 后端：SSE 的三个关键决定

### 4.1 同步生成器是安全的（查过源码，不是凭印象）

我原本说"生成器写成同步 `def`"，这话不能凭印象。翻了 Starlette 的 `StreamingResponse.__init__`：

```python
if isinstance(content, AsyncIterable):
    self.body_iterator = content
else:
    self.body_iterator = iterate_in_threadpool(content)   # ← 同步生成器走这里
```

**结论：写同步生成器是对的。** Starlette 会自动包进线程池，每取一帧跑在线程里，**不卡事件循环**。

### 4.2 ⚠️ 但代价是：一条流长时间占着一个线程

它是"**取一帧占一个 worker**"，而这里的"一帧"要等**一整个节点跑完**（检索 + 一次 DeepSeek，好几秒）。

```text
一条流在运行期间 → 长时间占着一个线程
默认线程池约 40  → 大约 40 个并发流就把池子打满
```

demo 完全够用，但这是一条**真实的并发上限**。

> ⭐ 这和你之前发现的"`engine` 懒加载不线程安全"是**同一类**：
> **能跑 ≠ 能并发跑。** 单机单人测试永远发现不了这类问题。

### 4.3 ⚠️ 生成器里的异常，全局 `exception_handler` 接不住

这是今天最该记住的一条。`@app.exception_handler(Exception)` 能返 500，**前提是响应还没开始发**。

```text
第一帧 yield 出去的那一刻 → 响应头和状态行已经发出去了
                          → 已经说过 "200 OK"
                          → 之后【改不成 500】了
异常只会让连接【突然断掉】—— 前端看到的是"卡住然后没了"，比 500 还难查
```

所以流式接口**必须自己在生成器内部兜住**，把错误变成一帧发出去。

> ⭐ **判据：边界变了，兜底的位置就得跟着变。**
> 昨天（10-13 §5.4）说"观测代码不能杀死业务代码"，今天说"流式接口不能指望全局兜底"——
> 同一个文件里，两种响应形态，兜底的位置就不一样。

## 5. 两个真实踩到的坑

### 5.1 ⭐ 静默 bug：`"round": "hops"`

```python
"round": "hops"     # ❌ 有引号 = 字符串。发出去的是字面的 h-o-p-s
"round": hops       # ✅ 没引号 = 变量。发出去的是 hops 里装的值
```

**这类 bug 最阴的地方：Python 完全不报错。** 服务照跑、日志照打，只有前端会发现"轮数怎么是个单词"。

```text
引号里面 → 给 JSON 看的【键名】 →  "type" / "round" / "hits"   本来就该带引号
引号外面 → Python 的【变量】     →  hops / update["answer"]     绝不能带引号
```

**自查法**：`{}` 里，**冒号左边**全是带引号的固定名字；**冒号右边**如果是个变量，就一定不能有引号。

有意思的是，同一个变量在 `final` 那帧里写对了 —— **一处写对一处写错**，说明不是不懂，是手滑。而手滑的 bug **只能靠逐行核对抓，不能靠报错**。

### 5.2 中文用户专属：全角引号导致 422

在 `/docs` 里试接口，报错：

```json
{"type":"json_invalid", "loc":["body", 16], "msg":"JSON decode error",
 "ctx":{"error":"Expecting value"}}
```

`loc: ["body", 16]` 是"读到第 16 个字符就读不动了"。数一下 Swagger 那个带缩进的 body：

```text
0:{  1:换行  2:空格  3:空格  4:"  5:q ... 13:"  14::  15:空格  16:"
                                                              ↑ 这里有问题的位置
```

第 16 位本该是**值的开引号**。它说"Expecting value"，意思就是**那个引号不是它认识的引号**。

**原因**：中文输入法下打 `"` 出来的是全角 `“`。**这俩在屏幕上几乎一样，电脑认为是完全不同的字符。**

```text
" 半角（英文）→ JSON 认        ：｛｝， 同样有全角版本
“ 全角（中文）→ JSON 完全不认
```

> **判据**：**只有"结构标点"（引号/冒号/花括号/逗号）必须半角。**
> 字符串里面的中文、句尾的 `？` 全角完全没问题 —— 它们在字符串【内部】。
> 判断标准很简单：**这些符号是"给 JSON 看的"，不是"给人看的"。**

`422` 和 `500` 的区分（10-12 就写进注释了）在这里第一次真正救场：**看到 422 就知道"我的代码一行都没跑"**，不用去翻业务代码。

## 6. 前端：一个 HTML 文件，三个"想当然会踩"的坑

前端是纯 `HTML + JS` 单文件，扔在 `static/index.html`，用 `/` 路由发出去。

### 6.1 ⚠️ 不能用浏览器的 `EventSource`

```text
EventSource  →  只会发 GET，而且【不能带请求体】
我们的接口    →  POST + {"question": "..."} 放在 body 里
                 ↓
              EventSource 办不到
```

改用 `fetch()` + `response.body.getReader()`，自己解帧。

### 6.2 切帧 + 中文断字

```js
buf += decoder.decode(value, { stream: true });   // ★ stream:true 不能省
while ((i = buf.indexOf("\n\n")) !== -1) { ... }  // ★ 用 while 不是 if
```

两个细节都有理由：

- **`stream: true`**：网络按"块"送，**一个汉字可能正好被切成两半**（前一半在这块、后一半在下块）。加了这个参数，解码器会把半截字攒着等下半截。不加，中文会偶尔冒乱码。
- **`while` 而不是 `if`**：**一次 `read()` 可能带回好几帧**。`if` 会漏掉后面的。

### 6.3 ⚠️ CORS：双击 HTML 文件是打不开的

最直觉的做法是"双击 `index.html` 用浏览器打开"。**不行。**

```text
双击打开 → 地址是 file:///E:/...
接口在   → http://127.0.0.1:8000
                            ↓
                    两个"源"不一样
                            ↓
        浏览器在请求发出【之前】就拦掉，控制台只说一句 CORS policy
        （连后端的请求日志都不会有，很容易误判成"后端坏了"）
```

**解法：从服务自己这里把页面发出去。** 加一个 `@app.get("/")` 返回那个 HTML 文件，地址就变成 `http://127.0.0.1:8000`，**同源**，畅通无阻。

顺带一个**演示上的好处**：以后给面试官就是**一个网址**，不用解释"先开这个文件、再开那个终端"。

### 6.4 ⭐ 渲染 Markdown：先转义，再套标记

第一版我用 `textContent`（纯文本）渲染答案——**安全，但格式全丢了**，`**加粗**` 和 `- ` 原样打出来。

正确的做法**不是二选一**：

```text
① 先把模型文本里的  <  >  &  全部转成 HTML 实体   ← 这一步之后，注入【不可能】发生
                ↓
② 再把 **xx** / `xx` / - xx 换成我们【自己写的】标签
```

**顺序是关键**：先转义，模型就算吐 `<script>alert(1)</script>`，也已经变成 `&lt;script&gt;` 这串**纯文字**，再也活不过来；第 ② 步产出的标签是我们自己拼的，安全。

实测四个用例（含一次注入尝试）：

```text
输入：**正常加粗** 然后 <script>alert('xss')</script> 还有 <img src=x onerror=alert(2)> 和 a<b>c
输出：<p><strong>正常加粗</strong> 然后 &lt;script&gt;...&lt;/script&gt; 还有
      &lt;img src=x onerror=alert(2)&gt; 和 a&lt;b&gt;c</p>
                ↑ 标记生效了、注入死了 —— 各干各的，不是二选一
```

**转义内部还有个顺序**：`&` 必须**第一个**替换。

```python
# ✅ & 先转：  a & b < c  →  a &amp; b &lt; c
# ❌ 顺序反了：a & b < c  →  a &amp; b &amp;lt; c   ← 把刚造的 &lt; 又转了一遍
```

因为 **`&lt;` 里面本身有个 `&`**。先转 `&` 就把它"保护"住了；后转就会产生**双重转义**，页面上冒出 `&lt;` 这种半截符号。

**诚实的说明**：这是**手写的迷你版**，只认加粗 / 行内代码 / 无序列表 / 标题四种，**不认表格、链接、嵌套列表**。要不要换成 `marked + DOMPurify`？

**先不换**——理由和 `retrieval.py` 里"BM25 自己实现、不依赖第三方库"是同一条：**现在这四种覆盖了模型实际会用的 95%，而且整个渲染逻辑能一眼读明白**。真遇到表格再换，换的时候"先消毒后渲染"那条底线照样不能丢。

data: {"type": "plan", "next": "BERT masked language model pretraining objective"}

## 9. 追补（同日下午）：token 级流式 —— "让文字一个个吐"

§0 论证过"token 级流式信息量不变、不加分"，所以第一版只做了**节点粒度**。
后来重看这个判断：**它错了**。`node_done` 里那次 LLM 调用是整条链路最长的纯等待
（实测占 41%），让用户盯着空屏等 2.8 秒，和看着字一个个蹦出来，体验差很远。
"信息量不变"是对的技术判断，**但流式的价值本来就不在信息量，在等待感**。下午补上了。

### 9.1 先测再定：`stream_mode="messages"` 能不能和阻塞的 `.invoke()` 共存

`node_done` 里是 `answer = _llm_text.invoke(prompt).content` —— **阻塞式**调用。
直觉上"阻塞"= 拿不到 token 流。去 `langchain_core` 源码找依据，`BaseChatModel._should_stream` 最后几行：

```python
# Affirmative: a v1 streaming callback handler is attached.
handlers = run_manager.handlers if run_manager else []
return any(isinstance(h, _StreamingCallbackHandler) for h in handlers)
```

**"挂上了流式回调就返回 True"** —— LangGraph 的 messages 模式挂了一个流式回调，
阻塞的 `.invoke()` 检测到它就自动改走流式接口。**`graph.py` 一行都不用改。**

实测（探针脚本，跑一道跨论文的题）：拿到 **61 个 message 块**，`judge` 17 块、`done` 44 块。

> ⭐ **判据：改的是"怎么要数据"，不是"怎么算数据"。**
> 所以整个功能没有一行落进 `agent/` —— Agent 层保持收尾状态。

### 9.2 ⚠️ judge 也在调 LLM，它的 token 会混进来

那 17 块 `judge` 的 token 是它在**写 JSON**：`{  "  enough  "  :  false  ,  "  query  "  :  ...`
一片一片的，直接显示页面就像坏了。所以必须过滤：

```python
piece, meta = data
if meta.get("langgraph_node") != "done":   # 元信息里有节点名
    continue
```

> ⚠️ **过滤掉的是"哪来的"，不是"哪个节点返回的"** —— `messages` 帧和 `updates` 帧是两回事：
> - `updates` = 节点的 **return 值**。每个节点跑完都有；`done` 的那一帧叫 `final`
> - `messages` = 节点**内部那次 LLM 调用**吐的 token。只有调了 LLM 的节点才有

实测（只订阅 messages，按节点分类；另一次运行的数字略有不同）：

| 节点 | 调 LLM 吗 | `updates` 帧 | `messages` 帧 |
|---|---|---|---|
| `collect` | 否（只做检索） | `progress` | **0 片**（没 LLM 可吐） |
| `judge` | 是 `_llm_json` | `plan` | 44 片 ← 被 `continue` 丢掉 |
| `done` | 是 `_llm_text` | **`final`** ← 它的 return 在这 | 451 片 ← 保留成 `token` |

**`done` 两种都发**：451 片 token 是"运行中"产生的，`final` 是"跑完"产生的。
所以"只有 done 走 message"这个说法是错的 —— **judge 也走，是我们选择丢掉它**。

### 9.3 ⭐ `mode` 不是"轮流发牌"，是"这一片是谁冒出来的"

`stream_mode=[A, B]` 不是两条流交替，而是**一条管道**，图在**任何一件事发生的当下**就往里塞一片，
每片贴个标签说明类别。两条实测证据：

**① 订阅了，但没那件事发生，就收不到。** 一个**没有任何节点调 LLM** 的小图，传两种 mode：

```
mode = 'updates'   data = {'a': {'n': 1}}
mode = 'updates'   data = {'b': {'n': 11}}
统计: {'updates': 2}        ← messages 一帧都没有
```

**② 真实那次提问，完全不交替。** 374 个元素的 mode 序列压缩后：

```
updates   x 3      ← collect / judge / collect 三个节点跑完
messages  x 370    ← done 里的 LLM 正在吐字
updates   x 1      ← done 跑完，返回 final
```

顺序就是"事件实际发生的顺序"：`messages` 是节点**运行中**产生的，`updates` 是节点**跑完**才有的
—— 所以必然"先有一堆 token，最后才有 final"。

> 补充：最终看到的序列 = **框架的事件顺序 + 你自己 `if` 的过滤**。
> judge 那轮的 messages 片被 `continue` 丢了，plan 帧被 `if not update["enough"]` 丢了。

### 9.4 ⚠️ `stream_mode` 从字符串改成列表，`for` 那一行必须跟着改

| `stream_mode=` | 每个元素的形状 |
|---|---|
| `"updates"` 字符串 | `{"节点名": {...}}` —— 直接能 `.items()` |
| `["updates"]` **单元素列表** | `("updates", {...})` —— **元组！** |
| `["updates", "messages"]` | `("updates", {...})` / `("messages", (块, 元信息))` |

> ⚠️ 判据是"**外面有没有方括号**"，不是"里面有几个元素"。`["updates"]` 只有一个，照样套元组。
> 只改 `stream_mode=` 忘了改 `for` 那一行 → `AttributeError: 'tuple' object has no attribute 'items'`（实测过）。

### 9.5 后端改动：只动了 `stream_mode` 一个参数

```python
stream_mode=["updates", "messages"]     # 原来是 "updates"
...
for mode, data in graph.stream(...):    # 原来是 for chunk in ...
    if mode == "updates":
        for node, update in data.items():   # 原有三条分支逻辑不动，只是缩进一层
            ...
    elif mode == "messages":
        piece, meta = data
        if meta.get("langgraph_node") != "done":
            continue
        if piece.content:      # 有些块是空的（比如整个回复的第一块）
            yield _sse({"type": "token", "text": piece.content})
```

### 9.6 ⭐ 前端：`citations` 和 `token` 的处理方式**正好相反**

今天最容易写反、而且**写反了不报错**的地方：

| | 后端每帧发什么 | 前端怎么做 | 写反的后果 |
|---|---|---|---|
| `citations` | **累计全量**（3 → 9 → 18） | 整个**替换** | 追加 → 30 条重复 |
| `token` | **一小段增量**（"BERT"、" 使"、"用"…） | 往后**追加** | 替换 → 只剩最后一个字 |

> ⭐ **判据：先问"后端这帧发的是全量还是增量"，再决定用 `=` 还是 `+=`。**

### 9.7 ⭐ `final` 是权威版本 —— 让流式自愈

token 阶段往 `#answer` 里攒的是**纯文本**（答案还没拼完，没法渲染 Markdown），
`final` 一到就整个覆盖成渲染好的 HTML。白送一个好处：**中间哪怕丢了几片 token，最后也会被修正回来。**
SSE 没有重传机制，一帧丢了就是永远丢了 —— 所以"最后一帧定稿"是必需的兜底。

配套加了 `finished` 锁：`final` 一到就上锁，之后再有 token 一律丢弃
（否则一句 `textContent +=` 会把刚渲染好的 HTML 整个冲掉）。CSS 上配 `#answer.streaming { white-space: pre-wrap }`
保住打字阶段的换行和空格。

### 9.8 实测

一次提问共 **374 帧**：`progress x1 → plan x1 → progress x1 → token x370 → final x1`

- **`token` 拼起来的文字和 `final.answer` 一字不差**（都是 787 字符）——
  打字机吐的和最后定稿的是同一份，不会"吐到一半变样"。
- **judge 的 JSON 碎片一片都没漏进来**：`enough` / `query` / `{` / `}` 出现次数全是 0。

### 9.9 代价

帧数从 6 涨到 374（**60 倍**）。自己用没事，但 §8.2 那条"~40 并发打满线程池"会更快撞上。

## 10. 追补（同日下午）：接 Langfuse —— 把"猜"变成"看"

### 10.1 先测再定：接之前先侦察，**省掉 4 个坑**

| 原本以为 | 实测结论 |
|---|---|
| 要自建（Docker 跑 6 个容器） | **不用**，云版免费额度够手工跑的量 |
| 要在 `.env` 里配 `HTTPS_PROXY` | **不用**。Clash 开着系统代理时，Python 的 httpx 会自动读 **Windows 注册表**里的代理设置（`trust_env` 的默认行为），环境变量里什么都没有也照样走代理 |
| 要手写 OTEL 的 span processor | **不用**。v4 的 `Langfuse()` 客户端内部自动做 |
| 缺密钥服务会起不来 | **不会**。实测只打印 `Client will be disabled` 就自己关掉，服务照常 |

> 顺带解释了一个怪现象：`curl.exe` 直连 `cloud.langfuse.com` 超时，但 Python 直连能通 ——
> 因为 **curl 不读 Windows 注册表，httpx 读**。所以"连线通不通"这个结论，取决于你用谁连。

### 10.2 ⚠️ 踩到并修好：装 langfuse 会把向量检索撞坏

`pip install langfuse` 之后项目**直接起不来**：

```
ModuleNotFoundError: No module named
  'opentelemetry.exporter.otlp.proto.common._exporter_metrics'
```

原因链：

```
langfuse  → 依赖 opentelemetry-*-proto-common      1.45.1  （被升上去）
chromadb  → 依赖 opentelemetry-...-proto-grpc       1.44.0  （留在原地）
             ↑ 这个包要配 common 1.44.0 的内部模块，对不上 → ImportError
chromadb 挂 → langchain_chroma 挂 → 整个向量检索挂 → 服务起不来
```

**修法**：把落单的那个也对齐到 1.45.1，并在 `requirements.txt` 里**显式钉死** ——
否则换台机器重装还会再踩（pip 只打一行 conflict warning，不会拦你）。

> ⭐ **判据：升级一个依赖，可能撞坏一个看起来毫无关系的模块。**
> 所以"装完包还能 import"必须实测，不能信 pip 那句 `Successfully installed`。

### 10.3 接线：`config={"callbacks": [...]}` —— 和 §9 是同一个机制

```python
from langfuse import Langfuse
from langfuse.langchain import CallbackHandler

langfuse_client = Langfuse()           # 读 LANGFUSE_* 环境变量
langfuse_handler = CallbackHandler()   # 挂到图上
...
graph.stream(
    make_initial_state(req.question),
    config={"callbacks": [langfuse_handler]},   # ← 就这一行
    stream_mode=["updates", "messages"],
)
```

> ⭐ **`config={"callbacks": [...]}` 和上午学的 `stream_mode="messages"` 是同一件事**：
> 都是跟图说"你每走一步顺便通知一下这个人"。
> 上午挂的是"把 token 给我"的回调，下午挂的是"把每一步记到 Langfuse"的回调。**同一个插槽，插不同的东西。**

### 10.4 ⚠️ 放错位置会**静默失效**：必须在 `graph` import 之后

```
.env 是被 config.py 的 load_dotenv 读进 os.environ 的
config 又是被 graph 间接 import 的
→ 把 Langfuse() 放在 graph import 之前，load_dotenv 还没执行
→ 读到空密钥 → "Client will be disabled"
```

**不报错，服务照常跑，你只是永远看不到数据。** 所以这两行放在了 `from graph import ...` 之后。

> 另外顺手修了两处**腐烂的注释**（§8.4 那条判据当场又应验一次）：
> lifespan 里那句"本项目没有需要清理的资源"—— 现在有东西要清理了（即 `flush()`）。

### 10.5 ⭐ 它解决了什么：从"猜"到"看"

一次真实提问（跨论文那道题）从服务器拉回来的完整 trace：

```
LangGraph                CHAIN        6.979s   ← 整次提问
├─ collect               CHAIN        1.444s   ← 第1轮检索
├─ judge                 CHAIN        1.594s   ← 第1轮判断
│   └─ ChatOpenAI        GENERATION   1.593s   ← LLM 调用被单独抓出来
├─ route_after_judge     CHAIN        0.000s
├─ collect               CHAIN        0.181s   ← 第2轮检索
├─ judge                 CHAIN        0.898s   ← 第2轮判断
│   └─ ChatOpenAI        GENERATION   0.897s
└─ done                  CHAIN        2.844s   ← 生成答案
    └─ ChatOpenAI        GENERATION   2.843s
```

| 花在哪 | 耗时 | 占比 |
|---|---|---|
| **大模型调用合计** | **5.333s** | **76%** |
| └ `done` 生成答案 | 2.843s | 41% |
| └ `judge` 两轮判断 | 2.490s | 36% |
| `collect` 检索合计（向量 + BM25 + 重排） | 1.625s | 23% |

**这就是以前拿不到的信息。** 混合检索 + 重排在优化上花了大力气，实际只占 23%；
**四分之三的时间在等大模型**，而 `judge` 占 36% 却只输出一个 `{"enough": false}`。
要提速该动的是 judge —— 这个结论以前只能靠猜。

而且**这棵树本身就是多跳的证据**：`collect → judge → collect → judge → done`，两轮循环一目了然。

### 10.6 ⭐ 额度用完会怎样？实测：**单纯不工作，毫发无伤**

用**故意写错的密钥**模拟（`load_dotenv` 默认不覆盖已有环境变量，所以命令行传的会赢）：

```
/health        → HTTP 200                    ← 服务活着
/ask/stream    → HTTP 200, 2.9 秒, 完整答案   ← 提问完全正常
uvicorn 日志里只有一行：
   Failed to export spans batch code: 401, reason: Unauthorized
```

原因：上报**不在请求链路上**。

```
请求线程                          后台线程
ask_stream()                      BatchSpanProcessor
  ↓ 跑图                            ↓ 攒够一批 / 等超时才发
  ↓ 每步产生 span                    ↓ 发失败 → 打一行日志 → 整批丢掉
  ↓ 丢进队列 ─────────────────────►  ↓ 不重试，不阻塞
  ↓ 继续跑（不等它）
  ↓ return
```

去源码确认了四件事：导出路径上**没有重试**（`backoff` 那个依赖只用在读数据集）、不阻塞请求线程、
队列满了丢新的、不抛异常。

> ⭐ **判据：可观测性组件必须能失败而不拖垮业务。**
> 这和 10-13 §5.4"观测代码不能杀死业务代码"是同一条线。
> 一个写错的 `print()` 能把业务炸掉；一个 trace 平台挂了不该影响你一个字节。

**紧急开关**：`.env` 里 `LANGFUSE_TRACING_ENABLED=false` 彻底关掉上报（源码 `client.py:366` 确认）。

### 10.7 ⚠️ 新 organization 用不了 legacy 的 trace 查询接口

想从服务器把 trace 拉回来验证时撞到：

```
410 LEGACY_API_UNAVAILABLE_FOR_NEW_ORGANIZATION
GET /api/public/traces 对 2026-09-16 之后创建的 organization 不可用
改用 GET /api/public/v2/observations?fromStartTime=<from>&toStartTime=<to>
```

SDK 里对应 `client.api.observations.get_many(...)`。
**这是会过期的知识** —— 照抄网上老教程用 `api.trace.list()` 会直接拿到 410。

## 11. 今天的产出（可写进简历的点）

1. **把 Agent 服务改造成 SSE 流式接口**：`POST /ask/stream` 按 LangGraph 的节点粒度推送进度，
   前端可实时看到多跳检索的每一轮推进**和每轮的检索词改写** —— 把"Agent 真的在跳"从
   一个 `hops` 数字变成了可见的过程。（同时保留非流式 `POST /ask` 供程序调用。）

2. **交付一个可直接演示的单页前端**：`GET /` 返回页面，输入问题即看到进度流、
   渲染后的答案与结构化引用来源。

3. **加上 token 级流式**：答案随生成逐字吐出（§9）。后端只动了 `stream_mode` 一个参数，
   **`agent/` 一行未改**。两条流（节点级 + token 级）在一个 `for` 里分流。

4. **接入 Langfuse 可观测性**（§10）：每次提问的完整轨迹自动上报，能看到每个节点的耗时、
   LLM 调用、以及多跳循环的结构。**第一次能量化"时间到底花在哪"** —— 实测 76% 在等大模型，
   而重排只占 23%。

5. ⭐ **一条判据**：**`print` 能看到的东西，不等于 `stream` 能拿到的东西。**
   日志读的是局部变量，数据流只拿得到 `return` 出去的东西。
   （10-13 是"打印把业务炸了"，今天是"打印看得到、别人看不着"，同一病根的两面。）

6. ⭐ **一条判据**：**先转义，再套标记 —— 顺序就是安全边界。**
   LLM 输出渲染成 HTML 时，转义必须在最前面；`&` 又必须在转义里排第一个（否则双重转义）。

7. ⭐ **一条判据**：**响应一旦开始发送，状态码就改不了了。**
   所以流式接口必须自己兜异常（全局 `exception_handler` 接不住"已经开始的响应"）。

8. ⭐ **一条判据**：**能跑 ≠ 能并发跑。**（§4.2 的线程池上限，和 `engine` 懒加载同类。）

9. ⭐ **一条判据**：**改的是"怎么要数据"，不是"怎么算数据"。**
   加 token 流式没碰 `agent/` 一行 —— 因为改的是取数方式。判断"这个改动该落在哪一层"，
   先问它是"数据的来源"还是"数据的产生"。

10. ⭐ **一条判据**：**先问"这帧是全量还是增量"，再决定用 `=` 还是 `+=`。**
    `citations` 每帧发全量（要替换），`token` 每帧发增量（要追加）。**两者写反都不报错。**

11. ⭐ **一条判据**：**升级一个依赖，可能撞坏一个看起来毫无关系的模块。**
    （`langfuse` 升了 opentelemetry 的公共包，把 `chromadb` 的 grpc exporter 撞死，
    整个向量检索 import 失败。）所以"装完还能 import"必须实测，不能信 pip 的 `Successfully installed`。

12. ⭐ **一条判据**：**可观测性组件必须能失败而不拖垮业务。**
    实测 Langfuse 密钥出错时，`/ask/stream` 照常 200、照常出答案，日志里只多一行 ERROR。
    （10-13 §5.4 是"观测代码不能杀死业务代码"，今天补上"观测平台挂了不能影响业务"。）

### 为什么第 5~12 条最该讲

因为它们**不是关于代码的发现，是关于"边界在哪"的发现**：

| 条目 | 边界画在哪 |
|---|---|
| 5 | **日志**和**数据**的边界 |
| 6 | **转义**和**渲染**的边界 |
| 7 | **响应前**和**响应后**的边界 |
| 8 | **单次运行**和**并发运行**的边界 |
| 9 | **数据的来源**和**数据的产生**的边界（该改哪一层） |
| 10 | **全量**和**增量**的边界（同一个字段，两种协议） |
| 11 | **一个依赖**和**另一个依赖**的边界（版本对齐） |
| 12 | **业务**和**观测**的边界 |

今天一天就撞出了四条新的边界 —— 而且全都是**不报错的错**：写反了就静默出错（第 10 条）、
放错位置就静默失效（§10.4）、升个包就把别处撞死（第 11 条）、平台挂了却不影响你（第 12 条）。
**唯一能发现它们的方法，是实测。**

和 10-08 的复现性量化、10-09 的控制变量实验、10-10 的"配置必须被读"、
10-12 的"测试要能区分对错"、10-13 的"观测代码不能杀死业务代码"是**同一条能力线**：
