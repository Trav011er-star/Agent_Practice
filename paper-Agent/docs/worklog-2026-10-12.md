## 1. 为什么是"先防雷"，而不是"先加功能"

这一步的顺序值得写清楚，因为它是**被下一步逼出来的**。

现在的运行方式是：**自己在终端敲 `python agent/graph.py`**。
崩了就崩了，报错打在自己屏幕上，改一行重跑。

下一步要做的是**服务化**（包成 HTTP 接口，让前端/别人能调）。一旦套上服务：

> **任何一次崩溃，都会变成用户看到的 500 错误。**

差别在于**谁能看到错误**：

| | 本地跑脚本 | 服务化之后 |
|---|---|---|
| 崩了谁受影响 | 只有我 | **所有调用方** |
| 报错在哪 | 我的终端 | **别人的屏幕上，一行看不懂的 500** |
| 我能不能立刻改 | 能，改完重跑 | 不能，得重新部署 |

所以结论是：

> **凡是在本地能崩的地方，服务化之后都会变成线上事故。**
> **加功能之前，先把已知会崩的地方堵上。**

这就是今天的全部动机。

## 2. ⭐ 防雷一：`node_judge` 的 JSON 解析容错

### 2.1 原来为什么会崩

`node_judge` 的活是"问大模型：证据够了吗"，模型返回一段 JSON 字符串。
原来只有一行：

```python
data = json.loads(reply.content)      # ❌ 裸调用
```

**它的假设是"模型一定会返回一个干净的、合法的 JSON 对象"。**
这个假设有三个漏洞：

| # | 模型可能返回 | 会抛什么 |
|---|---|---|
| ① | ` ```json {…} ``` `（Markdown 代码块包着） | `JSONDecodeError` |
| ② | `好的，我的判断是：{"enough": false, …}`（前后带废话） | `JSONDecodeError` |
| ③ | `["enough", true]`（合法 JSON，但**不是对象**） | `AttributeError`（list 没有 `.get`） |
| ④ | `None`（压根不是字符串） | `AttributeError`（`None.replace`） |

而且 ③④ 特别阴：**它们不是"JSON 格式错"，是"结构不对"**，
所以只抓 `JSONDecodeError` 是抓不住的。

### 2.2 两步清洗：先让它成功，实在不行才兜底

修的顺序**不能反**：

```text
     ① 先清洗，让本来能救的输入被救回来
              ↓
     ② 实在救不回来，才 try/except 降级
```

**反过来写（先宽抓、再清洗）是错的** —— 那样等于把能救的输入也一起扔了。

清洗函数 `_clean_json` 干两件事：

```python
# 第一步：删掉 Markdown 代码块围栏（固定子串，能枚举）
raw = raw.replace("```json", "")
raw = raw.replace("```", "")

# 第二步：截出最外层的花括号（废话不能枚举，用定位切片）
index1 = raw.find("{")      # 第一个 {  —— 最外层左括号必然最先出现
index2 = raw.rfind("}")     # 最后一个 } —— 最外层右括号必然是最后一个
raw = raw[index1 : index2 + 1]      # 切片左闭右开，所以 +1
```

两个地方的**方向**必须记清：

| | 从哪边找 | 返回 |
|---|---|---|
| `find` | 左 → 右 | **第一个**出现的下标 |
| `rfind` | 右 → 左 | **最后一个**出现的下标（r = right） |

> **「先删固定子串、再切首尾括号」这个套路，逼出了一个前提：**
> 「第一个 `{` 到最后一个 `}`」只有在**废话里不含花括号**时才正确。
> 如果模型说"你的问题是关于 `{注意}` 的，判断如下：{…}"，
> 就会从 `{注意}` 那个 `{` 开始切，切出来是残缺的。
>
> **这是个已知的近似，不是万无一失。** 好在它失败时会走下面的 try/except 兜底，
> 不会造成错误结果，只会降级。**清楚一个手法的适用边界，比会用更重要。**

### 2.3 用宽抓，但必须留痕

```python
try:
    raw  = _clean_json(reply.content)
    data = json.loads(raw)
    ...
except Exception as e:                      # ← 宽抓，故意的
    print(f"  [judge] [!!!] 解析模型返回失败：{type(e).__name__}: {e}")
    print(f"  [judge] 模型原始返回：{reply.content!r}")
    enough = True                            # 降级
    next_query = question
```

**为什么抓 `Exception` 而不是只抓 `JSONDecodeError`：**

判据是**"这段代码在谁的边界上"**：

| 场景 | 用什么 | 理由 |
|---|---|---|
| 内部逻辑（自己写的变量、自己的循环） | **窄抓** | 出了异常就是**我写错了**，要让它炸出来 |
| **系统边界**（模型输出、用户输入、网络） | **宽抓** | 输入方什么都干得出来，**枚举不完** |

`reply.content` 来自**大模型** —— 教科书级的系统边界。上面表格里那 4 种失败模式，
如果全用窄抓，就得写 4 个 `except`，而且模型明天还能发明第 5 种。

**宽抓的铁律 —— 必须把异常类型打出来：**

```python
print(f"...：{type(e).__name__}: {e}")       # ✅ 带类型
print("解析失败了")                          # ❌ 白抓
```

> 因为宽抓会把**所有**异常都吃掉，**包括我自己笔误造成的**。
> 哪天我把变量名敲错写成 `NamError`，也会被这里静默吞掉，
> 表现是"模型老是解析失败"，然后我查三天模型，其实是自己写错了。
> **`type(e).__name__` 就是那个"至少让我知道它是谁"的见证人。**

**宽抓的安全网**：`KeyboardInterrupt`（Ctrl+C）继承自 `BaseException` 而不是 `Exception`，
所以 `except Exception` **不会**吞掉 Ctrl+C，程序还能正常中断。

### 2.4 ⭐ 一个藏得很深的坑：字符串 `"false"` 是**真值**

模型可能给布尔 `false`，也可能给**字符串** `"false"`。所以不能直接：

```python
if data.get("enough"):        # ❌
```

因为：

```python
bool("false")   # True  ← 非空字符串一律为真！
bool("")        # False
```

**后果**：模型说"证据**不够**"，返回 `"false"`，程序读成"**够了**" ——
**语义完全反转**，而且**不报错**，静默地给出错误行为。

修法是**归一化**：不管来的是布尔还是字符串，统一转成小写字符串再比：

```python
enough = str(raw_enough).strip().lower() == "true"
```

| 输入 | `str()` 后 | `== "true"` |
|---|---|---|
| `True` | `"True"` → `"true"` | ✅ `True` |
| `"true"` | `"true"` | ✅ `True` |
| `" true "` | `"true"` | ✅ `True` |
| `"false"` | `"false"` | ✅ `False`（正确了！） |
| `None` | `"none"` | ✅ `False` |

### 2.5 `.get(k, default)` 和 `.get(k) or default` 的区别

`next_query` 这行的写法值得单独记：

```python
next_query = data.get("next_query") or question     # ✅ 用了这个
```

看起来 `.get("next_query", question)` 更"正统"，但**它漏了一种情况**：

```python
{"next_query": None}    # 键【存在】，值是 None
```

| 写法 | 键缺失 | 值是 `None` | 值是 `""` |
|---|---|---|---|
| `data["next_query"]` | 💥 `KeyError` | `None` | `""` |
| `data.get("next_query", question)` | `question` | **`None`** ❌ | **`""`** ❌ |
| `data.get("next_query") or question` | `question` | `question` ✅ | `question` ✅ |

**`.get(k, default)` 只管"键不存在"这一种情况** ——
键存在但值是 `None`，它会老老实实把 `None` 交给你。

而本项目的 prompt 里明明白白写着 `{"enough": true, "next_query": null}`，
**"键在、值是 null"是默认情况，不是边缘情况**。

**选哪个的判据：**

> - `None` / `0` / `""` **是有意义的值** → 用 `.get(k, default)`
> - 所有假值都等于"没有" → 用 `.get(k) or default`

这里所有假值都等于"没给下一轮的问题"，所以用 `or`。

### 2.6 第 2.5 节的后果为什么严重

如果这里写错，`state["query"]` 会变成 `None`，下一轮 `node_collect` 就会调
`retrieve(query=None)` —— 而 `retrieve` 当时**没有任何保护**（就是下面 §3 要修的东西）。

**一个字段的错误，会沿着 state 一路传到另一个节点的崩溃。**
这也是为什么 §3 那条兜底非加不可。

## 3. ⭐ 防雷二：`retrieve` 失败时降级

`node_collect` 里原本是裸调用：

```python
docs = retrieve(query=query, k=k)      # ❌ 检索炸了，整个图直接崩
```

`retrieve` 底下套着**三层**外部资源：向量库（Chroma）、BM25 关键词索引、rerank 模型。
任何一层出问题 —— 模型文件损坏、内存不够、数据库打不开 —— 都会往上抛。

修法：

```python
try:
    docs = retrieve(query=query, k=k)
except Exception as e:
    print(f"  [collect] [!!!] 检索失败：{type(e).__name__}: {e}")
    docs = []          # 降级
```

### 3.1 为什么降级成 `[]`，而不是 `return` 结束

**这是个关键设计选择，值得问一句"为什么不直接收工"。**

因为路由函数 `route_after_judge` 是靠 **`hops`** 判断跳出的：

```python
if state["enough"] or state["hops"] >= MAX_HOPS:
    return "go_done"
```

如果这里直接 `return {"answer": "检索失败"}`：

- `hops` **连加都没加**（`+1` 在函数后半段），永远是 0
- `MAX_HOPS=5` 那个刹车**永远踩不到** → **可能死循环**

而 `docs = []` 让流程**照常往下走**：

```text
检索失败 → docs=[] → fresh=[] → hops 照常 +1
   → judge 看到证据没变 → 判 enough=True → 正常收工
```

**降级成"这轮啥也没捞到"，比"直接结束"安全得多。**
因为流程每一步的**前提（hops 在推进）**还成立。

### 3.2 实测验证

把 `retrieve` 换成一个一定爆炸的假函数，实跑 `node_collect`：

```text
[collect] [!!!] 检索失败：RuntimeError: simulated: vector store unavailable
[collect] 第 1 轮：撒网 k=3，新收 0 条

hops   : 1        ← ✅ 轮次正常推进（判断跳出的依据还在）
items  : []       ← ✅ 降级成空
seen   : []       ← ✅
tried  : ['q']    ← ✅ 这轮问过的话被记账了
```

**没崩，流程正常往下走。** 这就是要的效果。

## 4. ⭐ 坑：兜底代码自己会崩（GBK 控制台）

原来 `except` 里打印的是 `⚠️`。在 Windows 的 **GBK 控制台**上：

```text
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'
```

**这个坑的可怕之处在于它的位置**：`⚠️` 在**异常处理分支里**。

```text
正常路径   → 不会执行到那行 → 一切正常
异常路径   → 走到那行 → 打印 emoji → 又抛新异常 → 兜底代码自己崩了
```

**也就是说：防雷代码在真正需要它的那一刻，才第一次暴露自己是坏的。**
而且此时整个 `except` 块已经被打断，连降级都执行不到。

修法：把**打印语句里**的 emoji 换成纯 ASCII/中文：

```python
print(f"  [collect] [!!!] 检索失败：...")
```

> 注释里的 `⚠️` **留着没关系** —— 注释永远不会被打印，碰不到编码问题。
> **只有会被 `print()` 出去的内容才需要管编码。**
>
> 顺带：`→`(U+2192)、`｜`(U+FF5C) 这两个符号 **GBK 是认的**（属于中日韩标点），
> 所以 `[judge] 第 1 轮 → 够了吗：…` 那行一直打印正常，不用改。
> **判据是"这个字符在 GBK 里有没有"，不是"它看起来像不像符号"。**

## 5. 一个关于「测试」的教训：**抓不到 bug 的测试**

今天在整理练习文件时（`agent/test.py`，一份 `_clean_json` 的学习存档），
发现它是**改之前的旧版** —— 里面 `}` 用的是 `find` 而不是 `rfind`。

于是顺手验了一下它自带的那个测试用例：

```python
string = "```json{123}```"
print(_clean_json(string))
```

结果很值得记：

| 用例 | `find` 版 | `rfind` 版 | 能区分吗 |
|---|---|---|---|
| `"```json{123}```"` | `'{123}'` | `'{123}'` | ❌ **一样** |
| `'```json\n{"enough": true}\n```'` | `'{…}'` | `'{…}'` | ❌ 一样 |
| `'{"next_query": {"q": 1}}'`（嵌套） | `'{"next_query": {"q": 1}'` **少一个 `}`** | 正确 | ✅ **只有它能** |

**原因**：`{123}` 里**只有一个 `}`** —— 第一个和最后一个**是同一个**。
所以 `find` 和 `rfind` 返回一样的下标，两版输出完全相同，测试当然通过。

**更糟的是**：`{123}` 本身**根本不是合法 JSON**，
就算清洗对了，`json.loads` 照样报错 —— 所以这个用例是**双重无效**：
既分不出对错，也没验证真正的目标（能不能解析成字典）。

> ### ⭐ 教训
> **测试的价值不在于"跑了没报错"，而在于"能不能把对的版本和错的版本区分开"。**
>
> 只写一个单花括号的用例，等于**给错的实现发了张通行证** ——
> 它不但没抓到 bug，还让我**以为已经验过了**，比没有测试更危险。
>
> **补测试时先问一句：如果我把实现改错，这个用例会红吗？**
> 不会红的用例，是装饰品。

这也是本项目**第一次**从"练习文件"里发现问题 —— 存档留着是有用的。

## 6. 环境坑：VSCode 突然不自动激活 venv 了

### 症状

新开终端，提示符前没有 `(venv)`，跑 `python` 用的是全局解释器。

### 排查（排除法）

| 检查 | 结果 |
|---|---|
| `venv/Scripts/` 里 `activate` / `Activate.ps1` 在不在 | ✅ 都在，venv 完好 |
| PowerShell 执行策略 | ✅ `RemoteSigned`，允许本地脚本 |
| **装了什么 Python 相关扩展** | 🎯 **`ms-python.vscode-python-envs`** |

`.vscode/settings.json` 里写着：

```json
"python-envs.defaultEnvManager": "ms-python.python:conda"
```

**翻译过来就是"默认用 Conda 来管环境"。**

但 `paper-Agent/venv` 是个**标准库 venv**（虽然是用 miniconda 的 python 建的，
`pyvenv.cfg` 里 `command = ... -m venv`，但他是个**独立 venv，不是 conda env**）。
新扩展按 conda 的路子找环境，找不到能接管它的，于是**不激活**。

### 为什么是「突然」

那两行**是 8 月 24 日就写进去的**，没人改过。

但**旧版** VSCode 只看 `ms-python.python` 扩展的逻辑（`python.terminal.activateEnvironment`），
**压根不读 `python-envs.*` 这两个设置**。等 `vscode-python-envs` 更新、开始接管之后，
它才第一次真正读到这行 —— 于是行为变了。

> **不是 venv 坏了，是 VSCode 换了一套规则来读它。**
> 这类"我没改任何东西，它自己变了"的事故，
> 第一反应应该是**"有东西升级了"**，而不是"我哪里改错了"。

### 修法

```json
{
    // 钉死本仓库用的解释器 —— paper-Agent/venv 是标准库 venv
    "python.defaultInterpreterPath": "E:\\Agent_Practice\\paper-Agent\\venv\\Scripts\\python.exe",
    // 打开终端时自动激活上面这个环境
    "python.terminal.activateEnvironment": true
}
```

**两处改动，各治一个病：**

| 改动 | 治什么 |
|---|---|
| 删掉 `python-envs.*` 的 conda 两行 | 别再让新扩展走 conda 那条路找环境 |
| 新增 `python.defaultInterpreterPath` 指向 venv | 明确告诉 VSCode「这个仓库的解释器就是它」 |

> **这份配置建议提交** —— 别人 clone 下来解释器路径就是对的，不用再踩一遍。
> 它是**仓库级**配置（在 `.vscode/` 下），**不会影响其他项目**里用 conda。
>
> **顺带记一笔**：venv 藏在 `paper-Agent/` 下一层，而工作区根目录是 `Agent_Practice`。
> **嵌套的 venv 本来就容易被自动探测漏掉。** 如果以后老出这毛病，
> 可以直接用 VSCode 打开 `paper-Agent` 文件夹，自动激活会稳得多。

## 7. 今天的产出（可写进简历的点）

1. **给 LLM 输出解析加了容错层**：面对模型可能返回的 4 类畸形输出
   （代码块围栏 / 前后废话 / 非对象 JSON / 非字符串），
   先**清洗**再**兜底**，把"模型不听话就崩"变成"逐步降级"。

2. **给检索层加了降级**：`retrieve` 在三层外部资源上任一层失败时，
   降级为空结果而不是让整个图崩溃 —— 并**实测验证**了降级路径
   （关键在于 `hops` 仍在推进，图不会死循环）。

3. ⭐ **一条判据**：**宽抓 `except Exception` 只该用在"系统边界"上，
   且必须打印 `type(e).__name__`** —— 否则自己的笔误也会被静默吞掉。

4. ⭐ **一条判据**：`.get(k, default)` **只防"键缺失"，不防"值是 None"**。
   当 `None` / `""` 也代表"没有"时（本项目 prompt 就明写 `"next_query": null`），
   要用 `.get(k) or default`。

5. ⭐ **一条方法论**：**测试要能区分对错才有价值**。
   一个所有版本都能通过的用例，是**装饰品**，比没有测试更危险
   （它提供的是**虚假的安心**）。

### 为什么第 3~5 条最该讲

因为它们**不是关于代码的发现，是关于"怎么判断"的发现**：

- 第 3 条回答的是"异常该在哪一层被接住"
- 第 4 条回答的是"两个看起来一样的方法，差在哪"
- 第 5 条回答的是"我怎么知道自己验对了"

这和 10-08 的复现性量化、10-09 的控制变量实验、10-10 的"配置必须被读"
是**同一条能力线**：**对自己的判断过程本身保持警觉。**
