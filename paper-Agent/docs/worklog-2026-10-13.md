## 1. 先测，再定阈值

第一反应是拍一个阈值："分数低于 X 就算无效"。

**这个想法必须掐死。** 拍出来的 X 会对两类问题同时生效：

```text
X 定高了  → 能答的问题被判成"无效" → 【误杀】，明明有答案却说"资料里没有"
X 定低了  → 无关的问题照样算"有效" → 【没用】，防雷形同虚设
```

误杀是更严重的错误。所以**在定 X 之前，先要知道真实分数长什么样。**

做法：写一个临时的 spy 脚本（放在系统临时目录，不污染仓库），
把 cross-encoder 对几组 (query, 片段) 的打分直接打出来：

```text
问题（英文）: What is the BLEU score of the big model on WMT 2014 English-to-German?
  正确片段   : +9.71   ✅
  无关片段   : -7.70   ✅
  另一个无关 : -10.26  ✅

问题（中文）: 大模型在 WMT 2014 英德翻译任务上的 BLEU 分数是多少？
  正确片段   :  -0.67  ⚠️ 同一篇文档！
```

### 1.1 ⭐ 关键发现：同一个问题，中英文差了 10 分

**同一个问题、同一篇文档，英文问是 +9.71，中文问是 −0.67。**

这不是测量误差，是**检索链路的结构决定的**：

```python
# agent/graph.py —— make_initial_state
"query": question,   # 第一轮的检索词 = 原问题
```

第一轮的 `query` **就是用户原话**。cross-encoder 是英文语料
（`cross-encoder/ms-marco-MiniLM-L-6-v2`）训出来的，你把一句中文直接怼进
(query, 英文片段) 这个 pair 里，它只能给出一个没信息量的低分。

于是：**中文用户的第一轮，天然就是最低分的那一轮。**

这一条直接决定了下一节的参数取值——它是**结构论证**，不是拍脑袋。

## 2. 阈值取 0：不是挑的，是"模型自己的分界线"

既然要定阈值，最"有依据"的取法是**问模型**：它认为多低算不相关？

去看重排模型本地的 `config.json`，里面有一行：

```json
"sbert_ce_default_activation_function": "torch.nn.modules.linear.Identity"
```

`Identity` 就是**什么都不做**（恒等函数）。这意味着：

```text
self.model.predict(pairs) 返回的是 【原始 logits】，没有过 sigmoid
```

而 cross-encoder 的训练目标是二分类（相关 / 不相关）。二分类里：

```text
logit > 0  ⇔  sigmoid(logit) > 0.5  ⇔  模型认为【相关】
logit = 0  ⇔  sigmoid(logit) = 0.5  ⇔  模型的决策边界
logit < 0  ⇔  sigmoid(logit) < 0.5  ⇔  模型认为【不相关】
```

**所以 0 不是我挑的数，是模型自己的决策边界。**

```python
MIN_RERANK_SCORE = 0.0
```

> **为什么要专门去翻 config.json**：如果这行激活函数是 `Sigmoid`，
> 那 `predict()` 返回的就是 0~1 的概率，阈值该取 0.5，取 0 就完全错了。
> **同一个数字，在两种输出约定下含义相反。**
> 在没确认"这个数是 raw logit 还是概率"之前，任何阈值都是猜的。

## 3. 计数上限取 2：中文第一轮 −0.67 逼出来的

有了阈值 0，第二个问题：**连续几轮低分才停？**

直觉方案是"一轮低分就停"（`MAX_WEAK_ROUNDS = 1`）。**这个方案会把中文问题全杀了：**

```text
中文用户提问
   ↓
第 1 轮：query = 原问题（中文）→ 分数 −0.67 < 0 → 判"无效" → 停
   ↓
❌ 第一轮就被判死。而它明明是【能答】的问题（英文问是 +9.71）
```

因为 §1.1 那条结构：**第一轮的 query 是原话，不是改写过的英文检索词。**
中文用户的第一轮注定低分，这是**结构性**的，不是运气。

所以上限必须是 2，意思是：

```text
第 1 轮低分 → 记 1 笔，但【不】停（给一次机会）
   ↓
judge 用英文改写 query（prompt 里明确要求 "必须是英文"）
   ↓
第 2 轮还是低分 → 记第 2 笔 → 停
```

**一次低分是"第一轮的结构性劣势"，两次连续低分才是"真的搜不到"。**

这两条的定法刻意不同，分开记：

| 参数 | 取值 | 依据是什么 |
|---|---|---|
| `MIN_RERANK_SCORE` | `0.0` | **原理**：raw logit 的决策边界 |
| `MAX_WEAK_ROUNDS` | `2` | **结构**：第一轮 query = 原问题，中文必低分 |

> ⭐ **一条方法论**：**用原理定阈值，用滞后计数保安全。**
> 这是两个不同的问题，用两种不同的机制解。
> "阈值"回答的是"这一轮的分数算好还是坏"；"滞后计数"回答的是"坏几次才该放弃"。
> 把它们混成一个参数（比如"分数低于 X 且连续 N 轮"），就再也说不清哪一半该改。

## 4. 把两个计数器合并成一个

一开始是两个字段：

```python
empty_rounds: int   # 这轮一条新片段都没捞到
weak_rounds:  int   # 这轮捞到了，但最高分低于阈值
```

用户提出：**这两个语义上是同一件事** —— "这轮没有拿到新的有效证据"。
（`empty` 其实就是"最高分 = 不存在"，是 `weak` 的一个特例。）

合并后：

```python
if len(fresh) == 0:
    top_score = None
    weak_rounds = state["weak_rounds"] + 1        # 空 = 极端低分
else:
    top_score = fresh[0].metadata.get("rerank_score")
    weak_rounds = state["weak_rounds"] + 1 if top_score < MIN_RERANK_SCORE else 0
```

### ⭐ 这不是"记账合并"，它改变了停止规则

看起来像纯粹的代码精简，实际不是。举例：

```text
三轮的判定结果依次是： [空, 低分, 正常]
MAX = 2

分开计数： empty=1（<2），weak=1（<2） → 都不触发 → 走到第 3 轮才停
合并计数： weak = 1 → 2（第 2 轮就够 2 了）→ 第 2 轮停
```

**合并后的行为严格更早**，而且**语义更对**：用户关心的是"连续两轮白跑"，
不关心这两轮具体是怎么白跑的。

> 合并的代价：丢掉了"空 vs 低分"的区分。但既然两者的**处置动作完全一样**
> （都是记一笔、看要不要停），这个区分就没有任何代码在用它。
> **只有在两件事需要【不同处置】时，才值得分成两个概念。**

## 5. 四个 bug 复盘

改这块代码踩了四个坑，每个都能提炼出一条判据。

### 5.1 `docs + doc` —— 类型不匹配

```python
docs = docs + doc      # TypeError: can only concatenate list (not "Doc") to list
```

`+` 要求左右**同类型**：`list + list` 拼接，`doc + doc` 也可以，
但 `list + doc` 不行。单元素追加用 `append`：

```python
docs.append(doc)
```

### 5.2 ⭐ 把"计数上限"当成"分数阈值"用

写成了：

```python
weak_rounds = state["weak_rounds"] + 1 if top_score < MAX_EMPTY_ROUNDS else 0
                                            ↑ 这里应该是 MIN_RERANK_SCORE
```

`MAX_EMPTY_ROUNDS` 的值是 `2`，于是**实际生效的阈值变成了 2.0**，而正解是 0.0。

为什么这个 bug 危险：它**不会报错**，只会让判据悄悄变严。回头看实测数据——

```text
中文·跨论文 第 1 轮的最高分是 +2.30
```

按正解 0.0，这轮是**有效**的（余量 2.30）；按 bug 的 2.0，这轮是**无效**的（余量只剩 0.30）。
**一个字的笔误，就把一轮真实有效的检索判成了白跑。**
而且因为 0.30 的余量太小，换个问题结果就会翻，属于"时灵时不灵"的隐藏 bug。

**根因是命名**：那个常量叫 `MAX_EMPTY_ROUNDS`（一个**轮数**），
却被用在了一个**需要分数阈值**的位置。所以修完顺手把名字也改对了：

```python
MAX_WEAK_ROUNDS = 2      # 轮数
MIN_RERANK_SCORE = 0.0   # 分数
```

> ⭐ **判据**：**名字里的量纲要对得上用法。** 名字骗人的时候，
> 笔误不会被任何工具拦住——它看起来"读得通"。

### 5.3 ⭐ 三元表达式不短路，`or` 才短路

想在一行里算 `weak_rounds`，写成了：

```python
# ❌ fresh 为空时 IndexError: list index out of range
weak = state["weak_rounds"] + 1 if fresh[0].metadata.get("rerank_score") >= 0 else 0
```

差别在于**求值顺序**：

```text
A or B          → A 为真就【不再算 B】  ← 短路
A if C else B   → 【先算 C】，再决定取 A 还是 B  ← 不短路
```

三元表达式的条件是**必须求值**的，所以 `fresh[0]` 在空列表上照样执行。
改成 `if / else` 语句，把危险表达式关进分支里：

```python
if len(fresh) == 0:
    top_score = None
else:
    top_score = fresh[0].metadata.get("rerank_score")
```

### 5.4 ⭐⭐ 观测代码不能杀死业务代码

`print` 那行：

```python
print(f"  [collect] 第 {n} 轮：撒网 k={k}，新收 {len(fresh)} 条，最高分 {top_score:.2f}")
                                                                        ↑ None 时爆
```

```text
TypeError: unsupported format string passed to NoneType.__format__
```

`top_score` 在"一条都没捞到"时是 `None`，而 `:.2f` 要求它必须是个数。

**这个坑的位置和 10-12 §4 那个 emoji 坑是同一类，而且更严重：**

```text
这是一行【观测代码】（只是为了让你看清图在干什么）
但它处在 node_collect 的【正常返回路径】上
   ↓
它一炸 → node_collect 整个炸 → 异常穿透 → /ask 返回 500
   ↓
【看日志的代码，把请求打挂了】
```

修法分两步，关键是第二步的思路：

```python
# 第一步：把危险的算法关进 if 里，算出【一个现成的字符串】
top_display = "—" if top_score is None else f"{top_score:.2f}"

# 第二步：这一行只负责拼接，不可能失败
print(f"  [collect] 第 {n} 轮：撒网 k={k}，新收 {len(fresh)} 条，最高分 {top_display}")
```

> ⭐ **判据（可以带走的一条）**：
> **观测代码的失败，绝不允许影响业务代码的结果。**
>
> 手段是：**先在安全的地方把值算成一个字符串，再把它拼进 f-string。**
> 这样危险只存在于那个 `if` 里，一个分支错了不影响另一个分支；
> 而最后的 `print` 只剩字符串拼接，逻辑上不可能抛异常。

## 6. 实测

用 `test_weak_rounds.py`（顺手从临时脚本转正，和 `test_api.py` 一样是**直接跑的脚本**，不是 pytest）。

### 6.1 分支一：检索失败

```
[collect] [!!!] 检索失败：RuntimeError: 模拟：检索挂了
[collect] 第 1 轮：撒网 k=3，新收 0 条，最高分 —
>>> hops=1 weak_rounds=1 citations=0
```

`最高分 —` 说明 `top_score = None` 那条分支**没有崩**（这正是 5.4 修掉的那行）。

> 有意思的是它 **1 轮就停了**，比我预期的 2 轮更早。原因在 `route_after_judge`：

```python
if state["enough"] or state["hops"] >= MAX_HOPS or state["weak_rounds"] >= MAX_WEAK_ROUNDS:
    return "go_done"
```

`enough` 排在最前面。而 `PROMPT_JUDGE` 里明写了：
"如果已经检索了多轮……始终找不到答案，**也判 enough = true**"。
所以这里 judge 先一步判了"可以作答了"，**计数器还没攒够就被 judge 抢答了**。

这不是 bug，是设计好的两条出口在互相配合：**judge 是主出口，计数器是保险丝。**

### 6.2 分支二：回归（确认没误杀）

| 问题 | hops | weak_rounds | citations | 判定 |
|---|---|---|---|---|
| 英文 · 单跳 BLEU | 1 | 0 | 3 | ✅ 正常 |
| 英文 · 跨论文 BERT/GPT-3 | 2 | 0 | 9 | ✅ 正常 |
| 中文 · 跨论文 | 3 | 0 | 18 | ✅ 正常（+2.30 → +9.11 → +5.76） |
| 中文 · 无关（法国首都） | **2** | **2** | 9 | ✅ 及时停 |

最后一行就是今天要的效果：**改之前是 5 轮 / 20 条 citations**（一路跳到 `MAX_HOPS`），
**现在是 2 轮停下。** 每轮最多 9 条引用，省下的不只是时间。

### 6.3 ⭐ 最关键的一次验证：误杀测试（走 HTTP 服务）

单独跑那道**中文版 BLEU 题**——就是 §1.1 里分数 −0.67 的那道：

```text
[collect] 第 1 轮：撒网 k=3，新收 3 条，最高分 -0.67
[judge]   第 1 轮 → 够了吗：True
>>> hops=1   答案里包含 28.4   ✅
```

**−0.67 < 0，按计数器它已经被记了一笔"无效"，但它没被停掉——**
因为 judge 看了证据内容，认为够了，`enough=True` 先一步出口了。

这验证了两件事：

1. **分数只是"保险丝"，不是"开关"。** 真判断内容够不够的是 judge，不是分数。
   分数只在 judge 一直说"不够"的时候才出来兜底。
2. **两条出口的顺序是对的。** `enough` 排在最前，所以 judge 的正面判断
   永远能压过计数器的保守判断 —— 这恰好保护了中文问题。

## 7. 遗留（明确记下来，不假装没问题）

### 7.1 `.get("rerank_score")` 无默认值 → 潜在 `TypeError`

```python
top_score = fresh[0].metadata.get("rerank_score")
...
weak_rounds = state["weak_rounds"] + 1 if top_score < MIN_RERANK_SCORE else 0
```

如果 `retrieve` 换了 `mode`（比如从 `hybrid_rerank` 换成 `hybrid`），
`rerank_score` 这个字段就**不会存在**，`.get()` 返回 `None`，
再拿去和 `0.0` 比大小 → `TypeError`。

**当前安全**（`engine.retrieve` 写死了 `mode="hybrid_rerank"`，且检索失败时走的是
`len(fresh) == 0` 那条分支，根本不会碰这行）。但这是一条**静默的耦合**：
`graph.py` 依赖 `retrieval.py` 必定写入某个 metadata 键，而这个约定没有任何地方声明。

> 记下来，不修。理由：现在修属于为假想场景加防御；
> 真正该修的时刻是"真的要换 mode"的那天，那时顺手加 `or -inf` 或断言更合适。

### 7.2 有一条路径没有被实测覆盖

```text
连续两轮低分 + judge 两轮都说"不够" → 靠【计数器】停下
```

今天实测到的"靠计数器停"只有**无关问题**那一例；
而"能答的问题被计数器误杀"这条路径**没被触发过**——中文 BLEU 那题被 judge 救下来了。

支持"它不会被误杀"的证据是**间接的**：三次英文改写后重查的分数
（+6.43 / +6.32 / +9.11）**全部远高于 0**。

**这是一条有理由的推断，不是已验证的事实。** 记在这里。

### 7.3 可选：`weak_rounds` 改名 `dry_rounds`

合并之后这个计数器数的是"没有拿到新的有效证据"，而"weak（低分）"只是其中一种情况
（另一种是"空"）。名字略窄。不影响正确性，属于可读性优化。

## 8. 顺手：终端启动从 3.3 秒降到近乎瞬时

排查一个无关的报错时量到的：

```text
不带 profile:  0.318 s
带 profile:    3.312 s   ← 其中两次 conda.exe 调用各占 ~1.4 s
```

原因是 PowerShell 的 profile 在**开终端时**就跑 `conda shell.powershell hook`
并 `activate base`，而我们**大部分时候根本不碰 conda**。

改成**懒加载**：先放一个同名占位函数，第一次真正敲 `conda` 时才初始化，
初始化完把占位函数删掉（避免递归），再转发这次调用。

```powershell
function conda {
    Remove-Item Function:\conda -ErrorAction SilentlyContinue
    (& "E:\miniconda3\Scripts\conda.exe" "shell.powershell" "hook") |
        Out-String | Where-Object { $_ } | Invoke-Expression
    conda @args
}
```

代价是 `conda activate` 要等第一次的那 ~1.4 秒。**但那是"我要用 conda 时"的代价，
不是"我每次开终端"的代价** —— 把成本挪到真正需要它的那一刻。

## 9. 今天的产出（可写进简历的点）

1. **给 Agent 增加了第二条停止条件**：连续 N 轮未获得有效证据即终止，
   把"无关问题空转到 `MAX_HOPS`"从 5 轮降到 2 轮（引用条目 20 → 9）。

2. ⭐ **一个"先测再定"的参数决策**：阈值不是拍的——
   先测量真实分数分布（发现了同一问题中英文差 10 分的现象），
   再翻重排模型的 `config.json` 确认输出是 raw logit，
   从而用**模型自己的决策边界 0** 作为阈值。

3. ⭐ **一条判据**：**阈值用原理定，滞后计数用结构定。**
   `MIN_RERANK_SCORE=0` 的依据是"raw logit 的 0 等概率"；
   `MAX_WEAK_ROUNDS=2` 的依据是"第一轮 query = 用户原话，中文必低分"。
   **两个参数两条依据，不是同一个数字拍两遍。**

4. ⭐ **一条判据**：**观测代码的失败不允许影响业务代码。**
   一行 `print` 里的 `{None:.2f}` 就能让整个节点抛异常、HTTP 500。
   解法是"先算成字符串，再拼接"。

5. ⭐ **一条判据**：**合并两个概念时，要检查它是否改变了行为。**
   `empty_rounds` + `weak_rounds` → `weak_rounds` 看起来是精简，
   实际把停止点从第 3 轮提前到了第 2 轮（有具体例子）。

### 为什么第 3~5 条最该讲

因为它们仍然**不是关于代码的发现，是关于"怎么判断"的发现**：

- 第 3 条：**两个参数，要能各自说出依据**（说不出依据的参数就是运气）
- 第 4 条：**分清哪些代码是"给结果用的"、哪些是"给眼睛用的"**
- 第 5 条：**改代码前先想"这会不会改变行为"，而不是"这看起来更干净"**

和 10-08 的复现性量化、10-09 的控制变量实验、10-10 的"配置必须被读"、
10-12 的"测试要能区分对错"是**同一条能力线**：
**对自己的判断过程本身保持警觉。**
