## 1. 为什么选 DeepSeek

一句话：**它兼容 OpenAI 的接口**。

意思是，它的 URL、请求体、返回体长得跟 OpenAI 一模一样，
**只要换个 `base_url` 就能用**——不用为它单独学一套 SDK。

代码上就是从 `langchain_ollama.ChatOllama` 换成
`langchain_openai.ChatOpenAI`，改三个参数：

```python
ChatOpenAI(
    model="deepseek-chat",
    api_key=...,                      # 注意是 api_key 不是 api_key_env
    base_url="https://api.deepseek.com",
)
```

好处还有个"简历向"的：**任何 OpenAI 兼容的服务都能用这一套接**
（Kimi、通义、vLLM 本地部署……），所以这不是"给 DeepSeek 写死了一段代码"，
而是**学会了一类服务的接法**。

## 2. 密钥管理：三条规矩

接云端 API 要一个 key。这个 key 一旦泄露，别人就能拿你的钱刷 token。
所以定了三条规矩：

| 规矩 | 做法 |
|---|---|
| **绝不写进代码** | 只写 `config.DEEPSEEK_API_KEY`，代码里看不到字面量 |
| **绝不提交** | 放进 `.env`，`.env` 在 `.gitignore` 里 |
| **代码里给兜底** | 读不到就**立刻报错**，不要带着空 key 去发请求 |

三条里的第三条今天救了我一次（见 §3）。

`config.py` 里：

```python
DEEPSEEK_API_KEY = os.getenv("DEEPSEEK_API_KEY", "")   # 读不到就是空串
...
if not config.DEEPSEEK_API_KEY:
    raise RuntimeError("没读到 DEEPSEEK_API_KEY")       # fail fast
```

**这个"提前报错"是有意设计的**，值得说一句：

> 如果不写这个检查，`api_key=""` 会被原样发给服务器，
> 然后返回一个 `401 Unauthorized`——**你要花时间去猜**"是 key 错了？网络问题？还是别的？"
> 写了检查，报错直接告诉你"没读到 key"，**排查范围瞬间缩到一件事**。

这个手法叫 **fail fast（快速失败）**：越早、越靠近根因的地方报错，越好。

> 另外记一笔：`.env` 是**一个纯文本文件**，不是"环境变量"。
> `load_dotenv()` 这个函数**做的事**才是"把它读成环境变量"。
> 不调这个函数，`.env` 就只是一坨没人看的文字。

## 3. ⭐ 坑一：`load_dotenv` 忘了调，key 读成空串

### 症状

启动就炸：

```
RuntimeError: 没读到 DEEPSEEK_API_KEY
```

### 排查

`.env` 文件明明建好了，内容也是对的。那问题只能在"读"这一步。

**关键认知**：`os.getenv("DEEPSEEK_API_KEY", "")` 读的是**进程的环境变量**，
不是那个文件。文件要变成环境变量，**必须有人去调 `load_dotenv()`**。

翻 `config.py`——`from dotenv import load_dotenv` 写了，**但从来没调用过**。

### 修法

在 `PROJECT_ROOT` 定义好之后加一行：

```python
from dotenv import load_dotenv

PROJECT_ROOT = Path(__file__).resolve().parent

# ---------- 环境变量 ----------
load_dotenv(PROJECT_ROOT / ".env")     # ← 漏的就是这一行
```

位置很重要：必须**在 `os.getenv(...)` 之前**执行。
所以放在模块顶层靠前的位置，比放在文件末尾稳妥。

### 关于"会不会被系统环境变量顶掉"

顺手搞清了一个容易混的问题。`load_dotenv` 的默认行为是 `override=False`，
含义是：

> **进程里已经有的环境变量，优先；`.env` 只补那些还没有的。**

所以优先级是：

```
系统/用户环境变量   >   .env 文件   >   代码里的默认值 ""
```

对本项目来说这是**好事**——`.env` 就是默认来源，
哪天真要临时覆盖（比如换一个 key 试），在终端 `export` 一下就行，不用改文件。

> 顺带：环境变量属于**进程**。系统变量 → 复制给终端 → 复制给 `python.exe`。
> 和"虚拟环境（venv）"**没有任何关系**——
> "虚拟环境"和"环境变量"两个词里，"环境"根本不是一个意思。

## 4. ⭐ 坑二：`**kwargs` 的打包与拆包

### 症状

```
NameError: name 'kwargs' is not defined
```

### 根因

写函数签名时漏了 `**kwargs`，但函数体里用了 `kwargs`：

```python
def get_llm_model():              # ❌ 签名里没有 **kwargs
    ...
    **kwargs                      # ❌ 这里的 kwargs 从哪来？
```

### `**` 出现的**位置**决定它是干什么的

| 位置 | 干什么 | 叫法 |
|---|---|---|
| **定义时** `def f(**kwargs)` | 把散的关键字参数**打包成字典** | 收集 |
| **调用时** `f(**d)` | 把字典**拆开**成关键字参数 | 拆包 |

```python
def f(a, b):
    print(a, b)

d = {"a": 1, "b": 2}
f(d)      # 💥 把整个字典当成【一个】参数 → f(a={'a':1,'b':2}) → 缺 b，TypeError
f(**d)    # ✅ 拆开 → 等价于 f(a=1, b=2)
```

**我当时只实现了"调用时的拆包"，没写"定义时的收集"**，
所以 `kwargs` 这个名字在函数作用域里**根本不存在**。

修法：签名补上 `**kwargs`。

### 为什么这个函数需要 `**kwargs`

因为它是**工厂函数**——把"造哪种大模型"的差异包在里面，
让调用方（`graph.py`）**一行都不用改**。

```python
def get_llm_model(provider=None, **kwargs):
```

`**kwargs` 的作用是"**来者不拒**"：调用方传什么额外参数，
都原样透传给底层的 `ChatOllama` / `ChatOpenAI`。

## 5. ⭐ 坑三：DeepSeek 的 JSON 模式跟 Ollama **不一样**

### 症状

接上 DeepSeek 之后，`judge` 节点报错——要求返回 JSON，但模型回的
不是合法 JSON（或者干脆报"response_format 用错了"）。

### 根因

两个模型家族"要求 JSON 输出"的**说法不同**：

| | 怎么说 |
|---|---|
| **Ollama** | `ChatOllama(..., format="json")` |
| **OpenAI 系**（含 DeepSeek） | `model_kwargs={"response_format": {"type": "json_object"}}` |

而且 OpenAI 系还有一个**特别容易踩的附加条件**：

> **你的 prompt 里必须出现 "json" 这个词本身。**
> 没写的话，API 直接报错（不是你格式写错了，是它**明确要求**你提到 json）。

这就是为什么这个 bug 在 `done` 节点炸、在 `judge` 节点没事：

- `PROMPT_JUDGE` 里写了"只输出一个 JSON 对象" ✅ 提到 json 了
- `PROMPT_DONE` 里**一个 json 字都没提** ❌

### 修法（两处）

**① 在工厂里做转换**，把 Ollama 的说法翻译成 OpenAI 的说法：

```python
format = kwargs.pop("format", None)          # 先把 format 摘出来
if format == "json":                          # ← 注意要写成 == "json"
    kwargs["model_kwargs"] = {"response_format": {"type": "json_object"}}
```

**② `done` 节点本来就该用"说人话"的模型，不该要 JSON。**

这是个**设计错误**，不只是参数错误——`done` 的任务是输出一段**给用户看的答案**，
要 JSON 干什么？所以真正该改的是换成 `_llm_text`（见 §6）。

### 顺带记一笔：`format` 这个名字不好

`format` 是 Python 的**内置函数**（`format(3.14, ".2f")` 那种）。
拿它当变量名会把它盖住。改成 `want_json` 之类更稳，回头改。

## 6. 两个大模型客户端：按"输出给谁看"分工

代码里现在**同时存在两个 LLM 客户端**：

```python
_llm_json = get_llm_model(provider=config.LLM_PROVIDER, format="json")
_llm_text = get_llm_model(provider=config.LLM_PROVIDER)
```

| 客户端 | 谁用 | 为什么 |
|---|---|---|
| `_llm_json` | `judge` | 它的输出是**给程序读的**，必须是机器能解析的 JSON |
| `_llm_text` | `done` | 它的输出是**给人看的**，自然语言就好，要 JSON 反而是负担 |

**判断用哪个的标准就一句话：输出给谁看？**

- 给**程序**看 → 要 JSON（结构化，程序好解析）
- 给**人**看 → 说人话

另外还有个小坑：`_llm_json` 和 `_llm_text` 是**模块级变量**，
所以**导入这个模块的时候就会创建两个客户端**。启动时看到
`[LLM] provider = deepseek` 打印**两遍**，就是它们俩，不是 bug。

## 7. ⭐ 坑四：配置写了**没人读**（同一个 bug 犯了两次）

> **今天最该记住的教训。**

### 第一次

`config.py` 里加了全局开关：

```python
LLM_PROVIDER = "deepseek"        # ollama 还是 deepseek
```

但 `src/llm.py` 里的函数默认值是：

```python
def get_llm_model(provider="ollama", **kwargs):    # ❌ 写死了 ollama
```

它**从来不读 `config.LLM_PROVIDER`**。
于是 `config.py` 里那个开关是**死的**——改它，什么都不会发生。

### 第二次（改完第一次之后又犯）

把默认值改了，`src/llm.py` 也会读配置了。然后转身在 `graph.py` 里写：

```python
_llm_json = get_llm_model(provider="deepseek", ...)   # ❌ 又写死了
```

**`config.LLM_PROVIDER` 又变成死的了。** 同一个 bug，隔了一天，原地重生。

### 教训

> **配置项不是"写了就算数"，要确认真的有人在读它。**
> 判据很简单：**把这个配置改成一个明显的错值，看程序行为变不变。**
> 不变，就说明没人读。

这个道理和 10-08 §5.2 的"改完没变化"是**同一个**：
那次是改了没被读到的变量（`or` 短路），这次是改了没被读到的配置。
**"我明明改了却没反应"——永远先问"这个东西真的被读到了吗"。**

## 9. ⭐ 但必须诚实地说：它**还没"完善"**

紧接着上面的成功，做了一次自我检查，得到一个**比成功更重要的结论**。

### 9.1 多跳**一次都没真正跑起来**

看输出：**第 1 轮 judge 就判"够了"，循环结束。**

于是那些精心搭的多跳机制——`query` 改写、`seen` 去重、`hops` 计数、
`route_after_judge` 那条回边——**这次一条都没派上用场**。

> 换句话说：**现在这个 Agent 的行为，跟 `RAG_v2.py`（检索一次+生成一次）几乎一样。**

### 9.2 为什么跑不起来？

**因为库里只有一篇论文。**

答案就在那几十个片段里，第一轮捞上来的 3 条里就有 28.4——
**judge 判"够了"是完全正确的**，问题不在 judge。

这跟 10-09 §8 的反思是**同一件事**，只是这次更清楚了：

| 症状 | 根因 |
|---|---|
| 一轮就结束 | 一篇论文，答案唾手可得 |
| `query` 改写没用上 | 一篇论文，改不改写都在同一片区域 |
| 复读问题（见下）测不出来 | 只跑了一轮，来不及复读 |

**所以下一步不是改代码，是加论文。**

### 9.3 一个"悬案"因此还没结

10-09 §10 记过一个已诊断的问题：**`judge` 会复读上一轮的 query**
（prompt 从来没告诉它"已经问过什么"）。

修法也是现成的：给 state 加 `tried: list[str]`，把试过的 query 喂进 prompt。

但这个 bug **必须靠多轮才能暴露**，而今天每次都第 1 轮结束，
**所以这个修复无法验证**——在只有一篇论文的库上改它，改了也不知道对不对。

**结论：先放着，等有了论文一起改。** 这不是拖延，是"没有验证手段就不动手"。
