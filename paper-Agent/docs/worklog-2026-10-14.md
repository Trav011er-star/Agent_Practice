## 2. 实验：先看清 `.stream()` 到底吐什么

写了个一次性脚本（**跑完即删，不入库**），挑一道**跨论文、要跳 3 轮**的题——单跳的题只会吐两次，看不出"推进"。

结果 **7 帧**：

```text
[1] collect  {'items':<3>, 'seen':<3>, 'hops':1, 'tried':<1>, 'citations':<3>, 'weak_rounds':0}
[2] judge    {'enough':False, 'query':'BERT masked language model pretraining objective'}
[3] collect  {'items':<9>, 'seen':<9>, 'hops':2, 'tried':<2>, 'citations':<9>, 'weak_rounds':0}
[4] judge    {'enough':False, 'query':'GPT-3 autoregressive language modeling ...'}
[5] collect  {'items':<18>,'seen':<18>,'hops':3, 'tried':<3>, 'citations':<18>,'weak_rounds':0}
[6] judge    {'enough':True,  'query':'BERT 和 GPT-3 的预训练目标有什么不同？'}
[7] done     {'answer':'根据资料，BERT 与 GPT-3 的预训练目标不同如下：…'}
```

### 2.1 形状：一帧 = 一个节点

```python
{ 节点名字 : 这个节点 return 的那个 dict }
```

所以消费的写法是 `for node, update in chunk.items()`：
**`update` 不是别的东西，就是那个节点 `return` 出来的 dict 本身。**

### 2.2 ⭐ 一个必须想清楚的发现：`citations` 是全量，不是增量

看第 3 列：`citations` 是 **3 → 9 → 18**，而 `hops` 是 **1 → 2 → 3**。

**这两个不是一回事：**

| 字段 | 给的是 | 因为 `node_collect` 里写的是 |
|---|---|---|
| `hops` / `weak_rounds` | **绝对值** | `"hops": n` |
| `citations` / `items` / `seen` | **全量列表** | `state["citations"] + citation` |

节点返回的是"**合并后的结果**"，不是"差分"。第 2 轮那帧里，前 3 条引用**又原封不动重发了一遍**。

于是 SSE 协议有两条路：

```text
路 A：每帧发全量 citations（前端直接替换）
路 B：生成器里记 last_len，只发新增的几条
```

**选路 A，理由不是省事，是正确性**：

> **SSE 是单向广播，没有重发机制。掉一帧就是永久丢了。**
> 走 B 的话，客户端少收一帧，那几条引用**再也补不回来**；
> 走 A 的话，下一帧自带纠错。**多传几个字节，换"丢了也能自愈"，值。**

代价是前端必须**替换**而不是**追加** —— 追加会变成 3+9+18 = 30 条重复。

## 3. ⭐ 打脸：`print` 能看到的东西 ≠ stream 能拿到的东西

我第一版协议里写了：

```json
{"type":"progress", "round":1, "hits":3, "top_score":2.30}
```

**`top_score` 从哪来？** 去 `node_collect` 的 `return` 里找 —— **没有。**

```python
# node_collect 真正 return 的
{"items", "seen", "hops", "tried", "citations", "weak_rounds"}    # ← 没有 top_score
```

它只出现在这两行：

```python
top_score = fresh[0].metadata.get("rerank_score")   # ← 局部变量
print(f"... 最高分 {top_display}")                    # ← 只拿去打印了
```

**根因**：

```text
print  读的是函数【内部的局部变量】 —— 函数自己造、自己用、用完就扔
stream 只能拿到节点【return 出去】的东西
```

> **这和 10-13 §5.4 那个 `{None:.2f}` 是同一个病根的两面：**
>
> | | 症状 |
> |---|---|
> | 10-13 | **打印挂了** —— 观测代码把业务代码炸了 |
> | 今天 | **打印看得到、别人看不着** —— 观测数据没进数据流 |
>
> 都源于同一个模糊认识："**日志里有**"和"**数据里有**"是两回事。

**三个选项：**

| | 做法 | 代价 |
|---|---|---|
| **1（选它）** | 不要分数，用 `weak_rounds` 表达"这轮有效/无效" | 0 改动 |
| 2 | 给 `State` 加 `top_score` 字段 | 动 `graph.py` 两行 |
| 3 | `stream_mode="custom"` + `get_stream_writer()` | 多一个概念，动 `graph.py` |

**选 1。** 前端能有"第 1 轮 3 条（无效）→ 改写 → 第 2 轮 9 条 ✓"这条叙事就够了；具体是 2.30 还是 9.11 是锦上添花。而且 `graph.py` 昨天刚收尾，**不该为观感动它**。

（选项 3 是 LangGraph **专门为这件事设计的**机制——把观感数据从节点里发出去，不污染业务 state。将来真要把分数搬上屏幕再用它，它比选项 2 干净。）

## 4. 后端：SSE 的三个关键决定

### 4.1 同步生成器是安全的（查过源码，不是凭印象）

我原本说"生成器写成同步 `def`"，这话不能凭印象。翻了 Starlette 的 `StreamingResponse.__init__`：

```python
if isinstance(content, AsyncIterable):
    self.body_iterator = content
else:
    self.body_iterator = iterate_in_threadpool(content)   # ← 同步生成器走这里
```

**结论：写同步生成器是对的。** Starlette 会自动包进线程池，每取一帧跑在线程里，**不卡事件循环**。

### 4.2 ⚠️ 但代价是：一条流长时间占着一个线程

它是"**取一帧占一个 worker**"，而这里的"一帧"要等**一整个节点跑完**（检索 + 一次 DeepSeek，好几秒）。

```text
一条流在运行期间 → 长时间占着一个线程
默认线程池约 40  → 大约 40 个并发流就把池子打满
```

demo 完全够用，但这是一条**真实的并发上限**。

> ⭐ 这和你之前发现的"`engine` 懒加载不线程安全"是**同一类**：
> **能跑 ≠ 能并发跑。** 单机单人测试永远发现不了这类问题。

### 4.3 ⚠️ 生成器里的异常，全局 `exception_handler` 接不住

这是今天最该记住的一条。`@app.exception_handler(Exception)` 能返 500，**前提是响应还没开始发**。

```text
第一帧 yield 出去的那一刻 → 响应头和状态行已经发出去了
                          → 已经说过 "200 OK"
                          → 之后【改不成 500】了
异常只会让连接【突然断掉】—— 前端看到的是"卡住然后没了"，比 500 还难查
```

所以流式接口**必须自己在生成器内部兜住**，把错误变成一帧发出去。

> ⭐ **判据：边界变了，兜底的位置就得跟着变。**
> 昨天（10-13 §5.4）说"观测代码不能杀死业务代码"，今天说"流式接口不能指望全局兜底"——
> 同一个文件里，两种响应形态，兜底的位置就不一样。

## 5. 两个真实踩到的坑

### 5.1 ⭐ 静默 bug：`"round": "hops"`

```python
"round": "hops"     # ❌ 有引号 = 字符串。发出去的是字面的 h-o-p-s
"round": hops       # ✅ 没引号 = 变量。发出去的是 hops 里装的值
```

**这类 bug 最阴的地方：Python 完全不报错。** 服务照跑、日志照打，只有前端会发现"轮数怎么是个单词"。

```text
引号里面 → 给 JSON 看的【键名】 →  "type" / "round" / "hits"   本来就该带引号
引号外面 → Python 的【变量】     →  hops / update["answer"]     绝不能带引号
```

**自查法**：`{}` 里，**冒号左边**全是带引号的固定名字；**冒号右边**如果是个变量，就一定不能有引号。

有意思的是，同一个变量在 `final` 那帧里写对了 —— **一处写对一处写错**，说明不是不懂，是手滑。而手滑的 bug **只能靠逐行核对抓，不能靠报错**。

### 5.2 中文用户专属：全角引号导致 422

在 `/docs` 里试接口，报错：

```json
{"type":"json_invalid", "loc":["body", 16], "msg":"JSON decode error",
 "ctx":{"error":"Expecting value"}}
```

`loc: ["body", 16]` 是"读到第 16 个字符就读不动了"。数一下 Swagger 那个带缩进的 body：

```text
0:{  1:换行  2:空格  3:空格  4:"  5:q ... 13:"  14::  15:空格  16:"
                                                              ↑ 这里有问题的位置
```

第 16 位本该是**值的开引号**。它说"Expecting value"，意思就是**那个引号不是它认识的引号**。

**原因**：中文输入法下打 `"` 出来的是全角 `“`。**这俩在屏幕上几乎一样，电脑认为是完全不同的字符。**

```text
" 半角（英文）→ JSON 认        ：｛｝， 同样有全角版本
“ 全角（中文）→ JSON 完全不认
```

> **判据**：**只有"结构标点"（引号/冒号/花括号/逗号）必须半角。**
> 字符串里面的中文、句尾的 `？` 全角完全没问题 —— 它们在字符串【内部】。
> 判断标准很简单：**这些符号是"给 JSON 看的"，不是"给人看的"。**

`422` 和 `500` 的区分（10-12 就写进注释了）在这里第一次真正救场：**看到 422 就知道"我的代码一行都没跑"**，不用去翻业务代码。

## 6. 前端：一个 HTML 文件，三个"想当然会踩"的坑

前端是纯 `HTML + JS` 单文件，扔在 `static/index.html`，用 `/` 路由发出去。

### 6.1 ⚠️ 不能用浏览器的 `EventSource`

```text
EventSource  →  只会发 GET，而且【不能带请求体】
我们的接口    →  POST + {"question": "..."} 放在 body 里
                 ↓
              EventSource 办不到
```

改用 `fetch()` + `response.body.getReader()`，自己解帧。

### 6.2 切帧 + 中文断字

```js
buf += decoder.decode(value, { stream: true });   // ★ stream:true 不能省
while ((i = buf.indexOf("\n\n")) !== -1) { ... }  // ★ 用 while 不是 if
```

两个细节都有理由：

- **`stream: true`**：网络按"块"送，**一个汉字可能正好被切成两半**（前一半在这块、后一半在下块）。加了这个参数，解码器会把半截字攒着等下半截。不加，中文会偶尔冒乱码。
- **`while` 而不是 `if`**：**一次 `read()` 可能带回好几帧**。`if` 会漏掉后面的。

### 6.3 ⚠️ CORS：双击 HTML 文件是打不开的

最直觉的做法是"双击 `index.html` 用浏览器打开"。**不行。**

```text
双击打开 → 地址是 file:///E:/...
接口在   → http://127.0.0.1:8000
                            ↓
                    两个"源"不一样
                            ↓
        浏览器在请求发出【之前】就拦掉，控制台只说一句 CORS policy
        （连后端的请求日志都不会有，很容易误判成"后端坏了"）
```

**解法：从服务自己这里把页面发出去。** 加一个 `@app.get("/")` 返回那个 HTML 文件，地址就变成 `http://127.0.0.1:8000`，**同源**，畅通无阻。

顺带一个**演示上的好处**：以后给面试官就是**一个网址**，不用解释"先开这个文件、再开那个终端"。

### 6.4 ⭐ 渲染 Markdown：先转义，再套标记

第一版我用 `textContent`（纯文本）渲染答案——**安全，但格式全丢了**，`**加粗**` 和 `- ` 原样打出来。

正确的做法**不是二选一**：

```text
① 先把模型文本里的  <  >  &  全部转成 HTML 实体   ← 这一步之后，注入【不可能】发生
                ↓
② 再把 **xx** / `xx` / - xx 换成我们【自己写的】标签
```

**顺序是关键**：先转义，模型就算吐 `<script>alert(1)</script>`，也已经变成 `&lt;script&gt;` 这串**纯文字**，再也活不过来；第 ② 步产出的标签是我们自己拼的，安全。

实测四个用例（含一次注入尝试）：

```text
输入：**正常加粗** 然后 <script>alert('xss')</script> 还有 <img src=x onerror=alert(2)> 和 a<b>c
输出：<p><strong>正常加粗</strong> 然后 &lt;script&gt;...&lt;/script&gt; 还有
      &lt;img src=x onerror=alert(2)&gt; 和 a&lt;b&gt;c</p>
                ↑ 标记生效了、注入死了 —— 各干各的，不是二选一
```

**转义内部还有个顺序**：`&` 必须**第一个**替换。

```python
# ✅ & 先转：  a & b < c  →  a &amp; b &lt; c
# ❌ 顺序反了：a & b < c  →  a &amp; b &amp;lt; c   ← 把刚造的 &lt; 又转了一遍
```

因为 **`&lt;` 里面本身有个 `&`**。先转 `&` 就把它"保护"住了；后转就会产生**双重转义**，页面上冒出 `&lt;` 这种半截符号。

**诚实的说明**：这是**手写的迷你版**，只认加粗 / 行内代码 / 无序列表 / 标题四种，**不认表格、链接、嵌套列表**。要不要换成 `marked + DOMPurify`？

**先不换**——理由和 `retrieval.py` 里"BM25 自己实现、不依赖第三方库"是同一条：**现在这四种覆盖了模型实际会用的 95%，而且整个渲染逻辑能一眼读明白**。真遇到表格再换，换的时候"先消毒后渲染"那条底线照样不能丢。

## 7. 实测

### 7.1 后端（`/ask/stream` 裸输出）

```text
data: {"type": "progress", "round": 1, "hits": 3}
data: {"type": "plan", "next": "BERT masked language model pretraining objective"}
data: {"type": "progress", "round": 2, "hits": 9}
data: {"type": "plan", "next": "GPT-3 autoregressive language modeling pretraining objective"}
data: {"type": "progress", "round": 3, "hits": 18}
data: {"type": "final", "answer": "根据资料，BERT 和 GPT-3 的预训练目标不同如下：…", "hops": 3}
```

**6 帧**，和实验完全对得上。两个设计点得到验证：

- **`enough` 过滤生效**：`judge` 节点实际跑了 **3 次**，但 `plan` 帧只发了 **2 条** —— 第三次是 `enough=True`，被 `if not update["enough"]` 拦住了。**拦掉的正是那条"假计划"**（`enough=True` 时 `query` 退回原问题，那是占位符不是计划）。
- **记事本对**：`final` 里 `"hops": 3` 是从 `collect` 帧里记下来的（`done` 节点只返回 `answer`，不带轮数）。

### 7.2 前端

浏览器开 `http://127.0.0.1:8000`，进度一行一行滚出来，跑完展开答案（列表/加粗正确排版）和引用来源。

## 8. 遗留

### 8.1 ⚠️ judge 有时会"停早了"

同一道题、同一份代码、`temperature=0`，两次运行结果不一样：

```text
实验那次：  collect → judge → collect → judge → collect → judge → done   3 轮，答全
另一次：    collect → judge → collect → judge → done                    2 轮，缺一半
```

第 2 轮 judge 就判了 `enough=True`，于是答案最后写"关于 GPT-3 的预训练目标，资料里没有提到"。

**`temperature=0` 也没能消掉这种抖动**（模型服务端本身不完全确定）。这是**答案质量**问题，不是**流程**问题，今天不处理，但记下来。

> 这条和 10-08 的"评测可复现性的边界"是同一条线：**能复现到什么程度，本身要有量化认识，不能默认"一样的输入必然一样的输出"。**

### 8.2 并发上限 ~40 条流

见 §4.2。demo 够用，真上线要换异步实现或调大线程池。

### 8.3 前端不支持表格 / 链接

见 §6.4。用到了再换 `marked + DOMPurify`。

### 8.4 注释里的数字会腐烂

`api.py` 里那句"State 里一共 9 个字段……所以正好 7 个"是 `weak_rounds` 加进来**之前**写的。今天改成 10 / 8，并在旁边加了一句"**改 State 的时候记得回来看一眼这儿**"。

**过时的注释比没有注释更坏** —— 因为它说得头头是道，读的人不会怀疑。

   LLM 输出渲染成 HTML 时，转义必须在最前面；`&` 又必须在转义里排第一个（否则双重转义）。

5. ⭐ **一条判据**：**响应一旦开始发送，状态码就改不了了。**
   所以流式接口必须自己兜异常（全局 `exception_handler` 接不住"已经开始的响应"）。

6. ⭐ **一条判据**：**能跑 ≠ 能并发跑。**（§4.2 的线程池上限，和 `engine` 懒加载同类。）

### 为什么第 3~6 条最该讲

因为它们**不是关于代码的发现，是关于"边界在哪"的发现**：

- 第 3 条：**日志**和**数据**的边界
- 第 4 条：**转义**和**渲染**的边界
- 第 5 条：**响应前**和**响应后**的边界
- 第 6 条：**单次运行**和**并发运行**的边界

和 10-08 的复现性量化、10-09 的控制变量实验、10-10 的"配置必须被读"、
10-12 的"测试要能区分对错"、10-13 的"观测代码不能杀死业务代码"是**同一条能力线**：
**对自己的判断过程本身保持警觉。**
