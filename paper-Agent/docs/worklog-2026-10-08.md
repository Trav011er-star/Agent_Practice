## 3. 从零理解 LangGraph

今天的主体。零基础，一步一步来。

### 3.1 类比先立住：一条流水线

```
[工位1] ──传送带──> [工位2] ──传送带──> [工位3]
```

| 车间里的东西 | LangGraph 里的叫法 | 说明 |
|---|---|---|
| 工位 | **节点 node** | 干一件事的地方，**本质就是一个普通函数** |
| 传送带 | **边 edge** | 决定下一步去哪 |
| 传送带上流动的箱子 | **state** | 工位之间传递的数据 |

### 3.2 state：图里流动的那个箱子

用 `TypedDict` 声明箱子里有哪些字段：

```python
class State(TypedDict):
    hops: int          # 已经跳了几轮
    items: list[str]   # 攒到的证据
```

`TypedDict` 是"继承字典、并指定键"的写法。节点里用 `state["hops"]` 这样读。

### 3.3 节点的唯一规矩

> **收一个 state 进来，返回一个 dict，表示"我要改哪些字段"。**

```python
def node_collect(state: State) -> dict:
    n = state["hops"] + 1
    return {
        "items": state["items"] + [f"第{n}轮的证据"],
        "hops": n,
    }
```

### 3.4 ⭐ 最容易踩的坑：返回的是**覆盖**，不是追加

假设箱子里现在是 `items = ["旧条目"]`：

```python
return {"items": ["新条目"]}                  # ❌ 旧条目没了！变成 ["新条目"]
return {"items": state["items"] + ["新条目"]}  # ✅ 旧的还在，["旧条目", "新条目"]
```

**`return` 的字段是覆盖、是替换**，不是往列表里 append。
没返回的字段则原样保留。

做"攒证据"这种累加逻辑时，必须**自己把旧值读出来拼进去**，
不能指望框架帮你追加。这个坑第一次写多跳 Agent 时几乎必踩。

### 3.5 条件边：让图"自己决定"下一步

普通边是硬连的（`a → b` 永远走 b）。要让图**分支**，用条件边：

```python
builder.add_conditional_edges(
    "judge",              # ① 从哪个节点出来
    route_after_judge,    # ② 谁来决定下一步（"路由函数"）
    {                     # ③ 映射表：路由函数的返回值 -> 真实节点名
        "go_done":   "done",
        "go_again":  "collect",
    },
)
```

路由函数也是个普通函数，规矩更简单：

```python
def route_after_judge(state: State) -> str:
    if ...:
        return "go_done"      # 返回的字符串
    return "go_again"         # 必须和映射表左边的 key 一模一样
```

**拼错 key 会直接报错**（框架会告诉你"这个返回值我没在映射表里找到"），
所以不用怕——拼错了会被当场抓住。

### 3.6 其它

- `START` / `END`：两个特殊标记，代表起点和终点。
- `builder.compile()`：可以理解成"检查图纸、准备开工"。
  它会静态检查边的指向有没有指向不存在的节点之类的错误。
- `graph.invoke({...})`：启动。参数是**初始 state**（箱子里一开始装什么），
  返回的是跑完之后的 state。

### 3.7 今天的成品

`agent/graph.py`：4 个节点（`collect` → `judge` → 分支 → `done`），
一个玩具版"收集证据直到够了就停"的循环。**证据还是假的**，
只为把 LangGraph 的机制跑通。

## 4. 实验一：故意写错的阈值（练调试）

写路由函数时，把"证据够了"的条件误写成 `if len(state["items"]) > 2`（本意是 `>= 2`）。

跑出来看到：

```
[judge] 现在有 2 条证据 ...
[judge] 现在有 3 条证据 ...
```

**第 3 轮才停**。从打印输出反推：

- 打印显示第 2 轮时已经有 2 条证据了，但**它没停** → 说明条件在 2 这里不成立
- `2 > 2` 是 `False`，`2 >= 2` 是 `True`
- → **`>` 写成了 `>=` 的反面，差了一个边界**

改成 `>=` 后，第 2 轮准时停。

**这段的价值不在修 bug，在练方法**：
不要盯着代码干看，**让它自己说话**——把关键变量打印出来，
从"它实际停在第几轮"反推"哪一行判断出了偏差"。
范围一下就缩小到具体那一个运算符。

## 5. 实验二：刹车 ⭐⭐

> **今天最值钱的一段。**

### 5.1 实验目的

把"证据够了"的条件设成**永远达不到**的数，这样**只剩刹车能停下循环**——
用来验证刹车（`MAX_HOPS`）到底是干嘛的、不写它会怎样。

### 5.2 ⭐ 第一次做错了：改错了变量

我说的是"把**够了的阈值**改成 99"。
实际操作改的是 **`MAX_HOPS = 99`**（刹车那个数）。

跑出来**和之前一模一样**，还是第 4 轮被"够了"停下。

**为什么一样？** 看那个条件：

```python
if len(state["items"]) >= 4 or state["hops"] >= MAX_HOPS:
```

用 `or` 连接两件事：

| 条件 | 当时的值 | 结果 |
|---|---|---|
| `items >= 4` | 第 4 轮时满足 | ✅ **满足** |
| `hops >= 99` | 最多才 4 | ❌ 不满足 |

**`or` 左边一满足就整车通过，右边那个（刹车）根本没被检查到。**

所以"输出没变"说明的不是"刹车正常"，而是"**刹车压根没被用上**"。

### 5.3 这次失误本身很有价值：改完没变化，有两种可能

> **① 改错了地方　② 真的没影响。必须分清。**

分不清，就会得出完全错误的结论——
比如"我把刹车调大/调小都没变化，所以刹车没用"（**错的**，
实际是你改的那个东西从来没被读到）。

这个道理和昨天重排那个实验是同一个：
**做对照实验时，必须清楚自己改的是哪个变量，以及改了之后"哪个东西应该发生变化"。**

### 5.4 改对之后：刹车真的能停下

保持 `MAX_HOPS = 5`，把**第一个条件**改成 99：

```python
if len(state["items"]) >= 99 or state["hops"] >= MAX_HOPS:
```

跑出来：

| 阈值 | 谁停的 | 停在第几轮 |
|---|---|---|
| `items >= 4` | "够了"条件 | 第 4 轮 |
| `items >= 99` | **刹车 `MAX_HOPS`** | **第 5 轮** |

**两次结果不一样了** → 这才叫"实验有效"：因为你改的变量真的起了作用。

### 5.5 一个容易忽略的细节：刹车是"干完活才踩"

注意它是**第 5 轮干完之后**才踩的：
`collect` 先收了第 5 条证据，`judge` 才发现 `hops=5 >= 5`。

所以 `MAX_HOPS = 5` 的含义是"**最多干 5 轮**"，
不是"最多干 4 轮"。

**规律**：刹车放在循环的**开头**（judge 节点），
所以在它生效之前，那一轮的工作已经做完了。
写真实 Agent 时记住：**这个值是"允许的最大轮数"，别指望它是"提前一轮拦住"。**

## 6. 实测：LangGraph 的默认 `recursion_limit` 是 **10007**

图里不写刹车会怎样？LangGraph 自己有个兜底：跑太多步会抛
`GraphRecursionError`，默认上限叫 `recursion_limit`。

**实测这个默认值是 10007**——不是很多中文文章里写的 25。
（25 是 LangChain 里老 agent 的默认值，被以讹传讹搬过来了。）

### 为什么这条重要

**10007 当保险丝太长了。**
真写出一个转不停的循环，等它报错的时候，
你已经在本地模型上白白烧掉几十分钟甚至几小时。

**结论：框架的兜底不能当业务超时用，必须自己写 `MAX_HOPS`。**

### 面试可以这么答

> "LangGraph 自带 `recursion_limit`，默认是 **10007**——我实测过，不是文档里常说的 25。
> 这个值当保险丝太长了。所以我在图里自己加了 `MAX_HOPS` 刹车，放在 judge 节点的路由里。
> **框架的兜底不能当业务超时用。**"

## 7. 下一步的设计：`agent/engine.py`（已讲解，**未动笔**）

### 要解决的问题

`collect` 要真的去检索。但检索器**很贵**：

- 打开 Chroma 向量库
- 把全部 129 个片段读出来建 BM25 索引
- 加载 cross-encoder 重排模型（要读磁盘上几十 MB 权重）

如果每轮 `collect` 都重建一次，跑 5 轮就是 **5 倍开销**，纯浪费。

### 设计：引擎只造一次

> **类比**：retriever 像一台咖啡机。你不会每杯都重新买一台、重新预热。
> 开机一次，之后每杯直接出。

代码里的手法叫**缓存**：`agent/engine.py` 里用两个模块级变量
（`_retriever` / `_reranker`）存住造好的引擎，
`get_engine()` 第一次调用真的去造，之后每次只是取出来。

节点里只负责"用"，调一个 `retrieve(query, k)` 就完事，
检索模式固定用 `hybrid_rerank`（就是昨天做实验选出来的那套）。

## 9. ⭐⭐ 重大发现：评测的"可复现性"被高估了

> **今天第二个最值钱的发现。它直接修正了 README 里的一句结论。**

### 起因

为了补回 `hybrid_rerank` 那行，重跑了完整三模式评测。跑完一看，**对不上**：

| 配置 | 已提交版本（今早那次） | 今晚这次 |
|---|---|---|
| dense Recall@1 / Recall@3 | 75.4% / 91.2% | **77.2% / 87.7%** |
| hybrid Recall@1 / MRR | 87.7% / 0.924 | **82.5% / 0.901** |
| hybrid_rerank | 91.2% / 96.5% / 0.939 | 91.2% / 96.5% / 0.939 ✓ |

而在此之前我核对过 diff：重建向量库后那次运行的 dense / hybrid
和已提交的值是**逐字节相同**的。

**也就是说：同一个数据库、同一份代码，跑两次，结果不一样。**

### 排查：每一步排除了一个错误假设

| 假设 | 检验 | 结果 |
|---|---|---|
| ① 评测代码里有随机性 | 同一 Ollama 进程连跑 2 次 | **逐位一致** → 排除 |
| ② 是重启 Ollama 导致的 | 杀掉 `ollama serve` 重启，再跑 | **仍逐位一致** → 排除 |
| ③ 向量库被动了 | 查 sqlite：`embeddings` **208 行**（129+52+27，三个集合都在），时间戳停在今天 10:38 | 库是好的 → 排除 |

**那就只剩一个解释：不同 Ollama 进程给出的查询向量不一样。**

### 关键证据：不看总数，看变化的"分布"

光比总指标没用，要**逐题**比。这一比，问题一下就清楚了：

```
500_hybrid:  R@1 变了 5 题 | R@3 变了 [] | R@5 变了 []
    #18  RR 1.00->0.50      #25  RR 1.00->0.50
    #35  RR 1.00->0.50      #49  RR 0.50->1.00
    #52  RR 1.00->0.50
```

**两条信息，非常干净**：

1. **R@3 / R@5 一个都没变** → 检索**捞到了什么**是稳定的。
2. **R@1 变的 5 题，全部是"第 1 名 ↔ 第 2 名互换"**（RR 1.00 ↔ 0.50）。

→ **内容稳定，抖的只是"近似并列时谁排前面"。**

### 机制

1. 查询向量由 Ollama 的 `nomic-embed-text` **实时**算出。
2. 不同的 Ollama 进程（线程数、批大小、内存自适应配置不同）
   算出的向量会有**极小**的浮点差异。
3. 论文里本来就有很多片段**分数接近**，这点差异足以让并列的两条**换个位次**。
4. **重排为什么不受影响？** cross-encoder 是**本地 torch 模型**，完全确定性；
   而且它只看"候选池里有哪些"，不看池内顺序——而候选池（top-20）是稳定的。

### 结论：不是 bug，但必须写进文档

**这不是代码错误**，是"浮点 + 近似并列"的固有现象。但后果很实在：

> **R@1 这类指标天生会抖 ±5 个百分点。**
> R@3 / R@5 / MRR（以及全部重排指标）是稳的。

**对简历的影响**：hybrid 领先 dense 的幅度，R@1 从 12.3pt 缩到 5.3pt。
但 R@3 的 **98.2% vs 87.7%** 完全不受影响——**这条才是真正该拿去讲的结论**。

### 教训

> **"可复现"是有前提的，必须说清前提。**
> 说"完全可复现"之前先问自己：换台机器呢？换个进程呢？换个模型版本呢？

还有一条更通用的方法论：

> **"同一个数变了"不等于"系统有问题"——要看变化落在哪。**
> 落在"并列换位"上，说明内容其实没变；
> 落在 R@3 上，那才是真的检索能力变了。

## 10. 今天产出的、可以写进简历的结论

**今天没有新的检索指标**——今天的工作是搭骨架，不是调指标。
但产出两条**工程结论**，都是面试里能展开讲的：

1. **多跳 Agent 的循环必须自带刹车。**
   实测 LangGraph 默认 `recursion_limit = 10007`，
   框架兜底不能当业务超时用；循环里必须显式设 `MAX_HOPS`。
2. **`return` 是覆盖不是追加**——LangGraph 节点累加证据时，
   必须显式回拼旧值，否则历史证据会被静默丢掉。

以及一条**方法论**（比上面两条更值钱）：

3. ⭐ **"改完没有变化"有两种可能：改错了地方，或真的没影响。**
   今天亲历了一次：把刹车调大后输出完全没变，
   原因不是"刹车没用"，而是**那个条件压根没被读到**（`or` 短路）。
   分不清这两者，就会把实现错误当成实验结论。
4. ⭐⭐ **量化了自家评测的"可复现边界"**：
   同一 Ollama 进程内连跑**逐位一致**；
   换一个 Ollama 进程，R@1 会抖 **±5pt**（hybrid 87.7% ↔ 82.5%），
   但 R@3 / R@5 / MRR **完全不动**。
   逐题定位到：变化**全部**是"第 1 名 ↔ 第 2 名互换"——
   即**浮点差异只影响近似并列的排序，不影响召回内容**。

### 为什么第 3、4 条最值钱

它和昨天重排那个结论是**同一个能力**：

- 你会**怀疑自己的方案**
- 你会**设计对照实验**把"思路问题"和"实现问题"分开
- 你会**如实报告不利结果**，而不是把负作用悄悄删掉

面试里这比任何单个指标都好聊。
