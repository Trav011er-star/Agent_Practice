## 0. 起点：今天之前项目是什么样

一个能跑通、但**说不清好坏**的 RAG demo：

- `RAG_v1.py` 单轮问答，`RAG_v2.py` 多轮问答（含 query rewrite 指代消解）
- `src/` 下四个模块：`loader.py`（PDF 解析）/ `splitter.py`（分块）/ `embedding.py`（向量化+Chroma）/ `llm.py`
- `chunk_size=1000` **硬编码在代码里**，路径是相对路径
- 没有评测、没有 README、没有统一配置
- 二进制文件（`.pyc`、Chroma 库文件）被提交进了 git

**核心问题不是功能少，而是没有任何一个数字能证明这套东西好不好。**
面试时只能回答"我用了 RAG"，答不上"效果怎么样、为什么这么设计"。

## 1. 工程化改造：把散落的参数收拢

### `config.py`（新建）

所有可调参数集中到一处。原来想试 `chunk_size=500` 得翻 6 个源文件，现在只改一行。

路径全部用 `PROJECT_ROOT = Path(__file__).resolve().parent` 拼**绝对路径**——
原来的相对路径换个目录敲命令就找不到文件。

### `ingest.py`（新建）

建库脚本，支持：

| 参数 | 作用 |
|---|---|
| `--chunk-size 500 1000 2000` | 一次建多组集合，用于消融实验 |
| `--rebuild` | 先删同名集合再建，解决"跑两次数据翻倍" |

两个细节：

1. **给每个片段打上稳定唯一的 `chunk_id`**（形如 `c500_0042`）。
   这是后面混合检索能实现的**前提**——向量检索和 BM25 两路结果必须靠同一个主键对齐，
   光比对文本内容不可靠（不同段落可能有完全相同的文字）。
2. **不加 `--rebuild` 重复运行时主动警告**"这是追加不是覆盖"，而不是默默把库搞脏。

### `src/health.py`（新建）

启动自检。所有入口脚本运行前先检查 Ollama 是否可用、需要的模型是否已下载，
把"连不上"这类毫无信息量的报错**翻译成可操作的中文提示**。

### 其它

- `src/embedding.py` / `llm.py` / `splitter.py` 改为读取 config
- `RAG_v1.py` / `RAG_v2.py` 清理死代码，加上自检守卫
- 新建 `.gitignore`、`README.md`

## 2. 排障记录（今天最耗时间的部分）

> 这四个坑全部记进了 `README.md` 的「常见问题排查」章节。

### 坑 1：`OLLAMA_HOST=0.0.0.0` 导致的诡异连接失败 ⭐

**症状**：`python ingest.py` 报
```
ConnectionError: Failed to connect to Ollama. Please check that Ollama is downloaded, running and accessible.
```
但 `curl http://127.0.0.1:11434/api/tags` **明明返回 200**。

**根因**：系统环境变量 `OLLAMA_HOST=0.0.0.0:11434`。

`0.0.0.0` 是**服务端监听地址**（表示监听所有网卡），**不是客户端连接地址**。
ollama 的 Python 客户端读了这个变量，去连 `http://0.0.0.0:11434`，
在 Windows 上直接抛：
```
ConnectError [WinError 10049] 在其上下文中，该请求的地址无效。
```
**而客户端把这个底层异常吞掉了**，统一报成上面那句看不出原因的话。

**怎么定位的**：打印出客户端实际使用的地址，确认它真的是 `0.0.0.0`：
```python
OllamaEmbeddings()._client._client.base_url   # -> http://0.0.0.0:11434
```
再显式传 `base_url="http://127.0.0.1:11434"` 验证成功（返回 768 维向量）。

**已规避**：`config.OLLAMA_BASE_URL` 显式写死，不受该环境变量影响；
自检发现冲突时也会打印警告。

### 坑 2：`ollama list` 返回空

**原因**：模型放在 `E:\Ollama\models`，不在默认目录。
命令行启动 `ollama serve` **不会自动继承** `OLLAMA_MODELS` 环境变量（桌面版会）。

**解决**：
```powershell
$env:OLLAMA_MODELS = "E:\Ollama\models"; ollama serve
```

### 坑 3：报 `status code: 502`

**原因**：系统代理（Clash 监听 `127.0.0.1:7897`）把发往 localhost 的请求也转发走了，
代理连不上后端就回 502。**根因通常还是 Ollama 没启动**，不要被这个错误码带偏。

### 坑 4：重排模型下载卡死

**原因**：huggingface.co **直连实测 12 秒零响应**（不是慢，是根本连不上）。
`hf-mirror.com` 实测 0.6s 返回。

**解决**：`config.py` 顶层设 `HF_ENDPOINT = "https://hf-mirror.com"`。

⚠️ 注意：`huggingface_hub` 是在 **import 时**就把 `HF_ENDPOINT` 读成常量的，
所以环境变量必须在导入它之前设好。放在 `config.py` 顶层是因为
任何入口脚本都会先 `import config`，因此一定生效——**放晚了不生效**。

### 附带修掉的一个自己的 bug

`_port_open(host=OLLAMA_HOST, port=OLLAMA_PORT)` 把默认值绑定在了**函数定义时**，
导致自检对错误端口报出错误的提示。改成 `host=None, port=None` 再在函数体里兜底。

### 清理 Chroma 的孤儿目录

`--rebuild` 会调 `delete_collection()`，但 Chroma 会**残留** VECTOR segment 的
UUID 文件夹。找到 3 个孤儿目录（`6401eb21` / `ca5d78cf` / `ccdf56a7`）。

**删除前先做了安全性验证**：扫描库里所有表的所有 UUID 形态的值（找到 654 个），
**没有一个**匹配这 3 个孤儿目录，确认它们真的没被任何地方引用。

删除后 9.4M → 8.4M，重跑评测确认功能正常。

## 3. 搞懂 Chroma 的底层结构

实际查库得出的结构（不是猜的）：

```
databases → collections → segments → embeddings → embedding_metadata
```

一个 collection 会被切成两半存储：

- **METADATA segment** — 存在 `chroma.sqlite3` 里
- **VECTOR segment** — HNSW 索引，存在那个 UUID 文件夹里，
  就是 `header.bin` / `data_level0.bin` / `length.bin` / `link_lists.bin`
  （**这就是"文件夹名字看起来像加密"的原因，其实是 segment 的 UUID**）

两个容易踩的点：

- `embeddings` 表里**不存向量**
- 片段正文存在 `chroma:document` 这个 key 下，页码在 metadata 里

## 4. 建评测集（今天的地基）

### `eval/gold_qa.json`（新建）

**57 条人工标注问题**，每题四个字段：

| 字段 | 说明 |
|---|---|
| `question` | 问题 |
| `gold_pages` | 标准答案所在页码。**部分题目接受 2 个页码**（如"28.4 BLEU"在第 0 页和第 7 页都出现） |
| `evidence` | 从 PDF 里**逐字**摘出的证据原文，做子串匹配（比较前先做空白归一化） |
| `reference_answer` | 参考答案 |

覆盖**事实、数字表格、名词定义、公式**四类。

### `eval/metrics.py`（新建）

| 指标 | 定义 | 衡量什么 |
|---|---|---|
| **Recall@k** | 前 k 个片段里至少有一个来自正确页面 | 该找的东西**有没有被捞出来** |
| **AnswerHit@k** | 前 k 个片段里**真的包含标准答案原文**（子串匹配） | 比 Recall 严格得多——落在正确页码 ≠ 捞到了那句话 |
| **MRR@10** | 第一个命中片段排名的倒数平均值 | 正确答案**排得靠不靠前** |

### `eval/run_eval.py`（新建）

一键跑评测，`--chunk-size` / `--mode` 都支持传多个值做对比，`--detail` 打印未命中明细。
结果存 `eval/results/latest.json`。

**整个脚本不调用任何生成模型，所以结果完全可复现。**

## 5. 实验一：chunk_size 消融

评测集 57 题，检索深度 k=10，模型 `nomic-embed-text`。

| chunk_size | 片段数 | Recall@1 | Recall@3 | Recall@5 | AnswerHit@1 | AnswerHit@3 | AnswerHit@5 | MRR@10 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **500** | 129 | **75.4%** | **91.2%** | **94.7%** | 50.9% | 73.7% | 77.2% | **0.841** |
| 1000 | 52 | 57.9% | 80.7% | 91.2% | 42.1% | 64.9% | 73.7% | 0.706 |
| 2000 | 27 | 54.4% | 84.2% | 93.0% | 45.6% | **75.4%** | **82.5%** | 0.702 |

**结论**：

1. **`chunk_size=500` 整体最优**：Recall@1 比 1000 高 **17.5 个百分点**，MRR 从 0.706 → **0.841**。
   说明这篇论文里"段落级"的语义单元更接近 500 字，切 1000 会把多个主题混在一起，
   稀释掉向量表示的区分度。
2. **`chunk_size=2000` 在 AnswerHit@5 上反超（82.5%）**：片段越大越容易"顺带"把答案原文包进去。
   但它 Recall@1 只有 54.4%，说明大片段会命中正确页面却排不靠前。
   这印证了 **Recall@k 和 AnswerHit@k 测的不是同一件事**，只看一个会得出错误结论。
3. ⭐ **原来代码里硬编码的 `chunk_size=1000`，正好是三个里面最差的。**
   这个结论只有做实验才能得到——**这就是做评测的意义。**

## 6. 实验二：混合检索（今天最大的提升）

### `src/retrieval.py`（新建）

手写实现整套检索链路：

- `tokenize()` + 停用词表
- **BM25**（Okapi，`k1=1.5`, `b=0.75`）
- **RRF（Reciprocal Rank Fusion，rrf_k=60）**
- `HybridRetriever` — 提供 `dense` / `hybrid` / `hybrid_rerank` 三种模式
- `Reranker` — cross-encoder，`sentence_transformers` 懒加载
  （这样没装 torch 时也不影响其它功能）

### 为什么用 RRF 而不是"分数加权求和"

向量检索返回**余弦距离**（0~2，越小越像），BM25 返回**无上界的相关性分数**
（可能 0.3 也可能 30）。两者**量纲完全不同**，直接加权求和需要反复调权重且不稳定。

RRF **只用排名不用分数**：

```
score = Σ 1 / (k + rank)
```

天然免疫量纲问题，也不需要调参。这也是它在工业界检索系统里流行的原因。

### 结果（`chunk_size=500`）

| 检索策略 | Recall@1 | Recall@3 | Recall@5 | AnswerHit@3 | MRR@10 |
|---|---:|---:|---:|---:|---:|
| dense（纯向量） | 75.4% | 91.2% | 94.7% | 73.7% | 0.841 |
| **hybrid（BM25 + 向量 + RRF）** | **87.7%** | **98.2%** | **98.2%** | **86.0%** | **0.924** |

**Recall@3 从 91.2% → 98.2%（57 题里只漏 1 题），AnswerHit@3 从 73.7% → 86.0%。**

**收益来自哪里**：主要是 BM25 那一侧。这篇论文里 `BLEU`、`WMT 2014`、`16,384`
这类**专有名词和数字**，向量模型对它们并不敏感（训练语料里见得少），
但关键词精确匹配一抓一个准。两路互补，融合后提升明显。

**AnswerHit@3 提升 12.3 个百分点尤其关键**——它意味着喂给大模型的片段里
"真的含有答案原文"的比例大幅提高，**直接决定最终生成的准确率**。

## 7. 实验三：重排 —— 预期与实测相反 ⭐⭐

> **这是今天最有价值的一段。**

### 预期

"召回 20 条 → cross-encoder 精排到 3 条"是标准做法，预期必然涨。

### 实测：第一个模型是负作用

| 配置 | Recall@1 | Recall@3 | Recall@5 | AnswerHit@3 | MRR@10 |
|---|---:|---:|---:|---:|---:|
| hybrid（不重排） | 87.7% | **98.2%** | 98.2% | 86.0% | 0.924 |
| + 重排 `BAAI/bge-reranker-base` | 78.9% | 93.0% | 96.5% | 84.2% | 0.860 |
| **+ 重排 `cross-encoder/ms-marco-MiniLM-L-6-v2`** | **91.2%** | 96.5% | **98.2%** | **87.7%** | **0.939** |

### 排查思路：先分清是"思路问题"还是"模型问题"

**没有直接删掉写"重排没用"**，因为两种可能性的处理方式完全不同。

**先验证代码没写错**：`hybrid_rerank` 是从 RRF 融合后的 **20 条**里精排到 10 条，
候选池比 `hybrid` 的 10 条**更大**，所以 recall 只会被**重排的排序**限制。

**再看证据**：`hybrid` 的 Recall@5 已经到 98.2%，说明正确答案基本都在融合结果的前 5 里，
**重排只要不乱动就能保住这个水平**。它却把 Recall@3 拖到 93.0%，
说明它在**主动把正确片段往下排**。

→ 结论指向**模型不合适**。

### 验证：换模型重测

新建 **`eval/rerank_compare.py`**，换模型一行命令：

```bash
python eval/rerank_compare.py --chunk-size 500
python eval/rerank_compare.py --model cross-encoder/ms-marco-MiniLM-L-6-v2
```

**结论**：`BAAI/bge-reranker-base` 虽然在国内最常被推荐，
但**训练语料以中文为主**，放到英文论文上是**负作用**（Recall@1 掉了 8.8 个百分点）。
换成在英文 passage ranking（MS MARCO）上训练的模型后，
**Recall@1 涨 3.5 个百分点，MRR 从 0.924 → 0.939**。

### 如实记录代价

换成对口的模型后也**不是全面胜出**：`Recall@3` 反而从 98.2% 掉到 96.5%。

因为最终只有 top-3 喂给大模型，这个点**不能只报喜**。
它换来的是"最相关的那条排得更靠前"（Recall@1 / AnswerHit@1 提升），
代价是"第 3 名附近的边际召回"变弱。**这是权衡，不是纯赢。**

### 配套的环境工作

- 装上 `torch` / `sentence-transformers`。
  中间发现**两个 pip 在往同一个 venv 并发安装**（有把包写坏的风险），停掉了较旧的那个。
- 官方 PyPI 下载 torch wheel（124 MB）只有 **191 KB/s**（要 11 分钟），
  阿里云镜像 **800 KB/s**（约 2.6 分钟）→ 换镜像。
- 重排模型权重走直连下载（约 1.1 GB，含加载共 727 秒）。
- `requirements.txt` 补齐依赖。

## 9. 今天产出的、可以写进简历的量化结论

1. 自建 **57 条**标注评测集（含**页码**与**逐字证据**两级判定标准），
   实现 Recall@k / AnswerHit@k / MRR@10 三个指标的**完全可复现**评测。
2. **chunk_size 消融**：发现硬编码的 1000 是最差配置，改用 500 后
   **Recall@1 提升 17.5 个百分点**（57.9% → 75.4%），MRR 0.706 → 0.841。
3. **自实现 BM25 + RRF 混合检索**：**Recall@3 91.2% → 98.2%**，
   AnswerHit@3 73.7% → 86.0%，MRR 0.841 → 0.924。
4. ⭐ **重排的对照实验**：证明"重排必涨"是错的——
   模型不对时是负作用（Recall@1 87.7% → 78.9%），
   换成语言对口的模型后才涨（→ 91.2% / MRR 0.939），
   并**如实记录其 Recall@3 的代价**。

### 第 4 条为什么最值钱

它证明的不是"我用了重排"，而是：

- 你会**怀疑自己的方案**
- 你会**设计对照实验**把"思路问题"和"实现问题"分开
- 你会**如实报告不利结果**，而不是把负作用悄悄删掉

面试里这比任何单个指标都好聊。
