## 1. `agent/engine.py`：引擎只造一次

### 1.1 为什么需要它

检索本身很贵，一次 `retrieve()` 背后要做三件事：

1. 打开 Chroma 向量库，把 129 个片段读出来建 BM25 索引
2. 加载 cross-encoder 重排模型的权重（磁盘上几十 MB）
3. 加载 embedding function

而多跳的**每一轮** `collect` 都要检索一次。如果每轮都从头造一遍，
跑 5 轮就是 **5 倍开销**，而且第 2 轮开始纯粹是浪费——库没变，索引没变。

### 1.2 写法：模块级缓存

```python
_retriever = None      # 模块级变量：整个进程里只有这一份
_reranker  = None

def get_engine():
    global _retriever, _reranker     # 声明"我要给外面的这俩赋值"
    if _retriever is None:           # 第一次调用：造
        vector_store = load_vector_store()
        _retriever = HybridRetriever(vector_store)
        _reranker  = Reranker(...)
    return _retriever, _reranker     # 之后每次调用：直接取
```

两个知识点：

- **`global`**：函数里给**模块级变量**赋值，必须先用 `global` 声明，
  否则 Python 会以为你新建了一个局部变量，外面那个 `None` 一直不动。
- **缓存的判据是 `is None`**：第一次一定是 `None`，所以会进 `if` 造；
  造完就不再是 `None` 了，后面每次都跳过。

节点里从此只管"用"：`retrieve(query=query, k=k)`，别的不管。

### 1.3 写的时候漏了两行

第一次跑就炸了：`AttributeError: 'NoneType' object has no attribute ...`。
根因很蠢——`get_engine()` 里那个 `if _retriever is None:` **分支是空的**，
只写了 `if`，忘了在分支里真的去构造。

**教训（值得记）**：

> 写了 `if xxx is None:`，就必须保证**分支里真的赋值了**。
> 空分支**不会报错**，它只是"下次进来还是 `None`"，然后在下游某个不相干的地方炸掉。
> 这种 bug 的特征是：**报错的位置和出错的位置不在一起**。

修法就是补上 `vector_store = load_vector_store()` 和 `_retriever = HybridRetriever(vector_store)` 两行。

## 2. `collect` 换成真检索

### 2.1 去重：为什么必须记 `seen`

多跳每一轮都会重新检索，而检索是**近似**的——第 2 轮的 top-3 里很可能
有第 1 轮已经收过的片段。不去重的话，`items` 里会堆一堆重复文本，
占满上下文还让 `judge` 误以为"证据很多"。

所以 state 里加了 `seen: list[str]`，装**已经收过的 `chunk_id`**。
`chunk_id` 是 `ingest.py` 建库时给每个片段编的号（形如 `c500_0074`），
是这条片段在库里的唯一身份证。

```python
fresh = [d for d in docs if d.metadata["chunk_id"] not in seen]
```

**注意 `chunk_id` 是 `ingest.py` 自己加进去的**，不是 chromadb 或 PyMuPDF 给的。
第一次用 `chunk_id` 之前得先确认库里真有这个字段——没有的话
`d.metadata["chunk_id"]` 会直接 `KeyError`。

### 2.2 出处标签

证据要带出处，才能在最终答案里引用。写了个小函数生成标签：

```python
def _source_label(doc) -> str:
    paper = Path(doc.metadata.get("source", "?")).stem   # 去掉路径和 .pdf
    page  = doc.metadata.get("page", "?")
    return f"[{paper}, p.{page}]"
```

于是 `items` 里每条长这样：

```
[Attention Is All You Need, p.7] On the WMT 2014 English-to-German translation task, ...
```

**这个标签一路传到了最终答案里**，是本轮最直观的成果之一。

> 已知瑕疵：`page` 是 **0 起算**的（PyMuPDFLoader 的行为），
> 所以 `p.7` 其实是 PDF 的第 8 页。做 demo 时要么 +1，要么在文档里说明。

## 3. `judge` 换成 LLM 判断

### 3.1 prompt 的五个部件

第一次认真写 prompt，总结出一个结构（后面写别的 prompt 都按这个来）：

| 部件 | 在本例里 |
|---|---|
| ① 角色 | 你是一个检索质量评审员 |
| ② 任务 | 判断"证据"够不够回答"问题" |
| ③ 输入 | `{question}` / `{evidence}`，用 `【】` 框起来 |
| ④ 约束 | 严格一点；明确给出"什么算不够" |
| ⑤ 输出格式 | 只输出 JSON，给出两个样例行 |

其中**⑤ 里的样例行**（`{{"enough": true, ...}}`）特别有用——
大模型照着例子填比自己想格式靠谱得多。

> 注意 `{{` 和 `}}`：因为用了 `.format()`，**花括号要写两个**才是字面量。

### 3.2 为什么"严格一点"要配一个**具体例子**

只写"严格一点"是**抽象要求**，小模型接不住。
所以加了一句具体的：

> 如果只答对了一半（比如问的是英文→德文，却只找到英文→法文的数据），算**不够**

这是从**实际观察到的失败**倒推出来的——第一次它把英文→法文的 BLEU
当成了英文→德文的答案，回了 `enough: true`。

**prompt 不是想出来的，是看着模型怎么错、一条一条补出来的。**

## 4. 调试记录（两次"输出没变"）

### 4.1 `retrieve(question)` 忘了传 `k`

`retrieve` 的签名是 `retrieve(query, k=None)`，`k=None` 时取默认
`RETRIEVE_K = 3`。写 `collect` 时只写了 `retrieve(query=query)`，
于是**每一轮都固定取 3 条**，`k = 3*n` 白写了。

**症状很有指示性**：

```
[collect] 第 1 轮：撒网 k=3，新收 3 条
[collect] 第 2 轮：撒网 k=6，新收 0 条     ← 第 2 轮一条新的都没有
```

**为什么是 0**：还是那 3 条，全在 `seen` 里，全被过滤掉了。

**教训**：有默认值的参数最危险——**不传不报错，只是静默用了另一套行为**。
排查时看到"新收 0 条"就该立刻想到"取的东西是不是跟上一轮一模一样"。

### 4.2 路由阈值写错，永远停不下来

路由函数写的是：

```python
if state["enough"] or state["hops"] >= 99:   # ❌ 99 永远到不了
```

结果 ran 到 `MAX_HOPS` 才停。**同一类错误**：
写的值和你想的语义不一致。改回和 `MAX_HOPS` 挂钩就对了。

## 5. `k = 3 * n`："撒大网"这个 hack

### 5.1 它是什么

第 n 轮取 `3n` 条，去重后**恰好**新增 3 条：

| 轮次 | 撒网 k | 累计 `seen` | 新收 |
|---|---|---|---|
| 1 | 3 | 3 | 3 |
| 2 | 6 | 6 | 3 |
| 3 | 9 | 9 | 3 |

**它想解决的问题**：`retrieve(query, k)` 是个**无状态**函数。
它不知道"上几轮收过什么"。所以同一轮里想要"再来 3 条新的"，
只能**多取一些、自己筛**。取 3n 是保证筛完还剩 3 条的**充分**条件
（只要前 3n 名里包含了前几轮的全部 n-1 组）。

### 5.2 必须说清楚：这是**教学用的简陋补丁**，不是正解

它有三个硬伤，今天用一次长跑 **实测** 把前两个验证了：

**硬伤一：假设"排名稳定"**
它赌的是"第 n 轮取的前 3n 条里，包含了前几轮的那 3(n-1) 条"。
但检索排序是**近似**的（见 10-08 §9 的浮点抖动），
一旦某条老片段掉出前 3n，就会出现**漏收或重复**。

**硬伤二：只会"沿长度扩展"，不会"换方向"**
第 2 轮取 6 条 = 前 3 条 + 后 3 条。**本质上还是在同一片区域里挖**，
只是挖得深一点。真正的多跳应该是**换一个 query 去挖另一个区域**——
而那时候 `query` 确实变了，但 `k=3n` 这个设计让"最后 3 条"和"新 query 的前 3 名"
是两码事，混在一起就说不清新增的到底来自哪个 query。

**硬伤三：会退化**（本轮实测踩到）
`HYBRID_CANDIDATE_K = 20` 是候选池的上限。而 `k` 一路涨到 21/24/27/30 时**已经超过池子大小**：

```
第 7 轮  k=21  → 池子里只有 20 条，取不满
第 8 轮  k=24  → 新收 0 条     ← 池子被掏空了
第 9 轮  k=27  → 新收 0 条
第10 轮  k=30  → 新收 0 条
```

`k` 超过候选池之后，**"撒大网"这张网已经比池子还大**，
后面几轮纯粹是空转 + 白花钱。

### 5.3 正解应该是什么（下次改）

```python
k = 3          # 固定值，不再随轮次变
```

理由：让 **`query` 成为唯一的变量**。这样每轮新增什么，完全由"query 变了"
解释——这才是干净的可归因设计，也才讲得清"多跳到底有没有用"。

补充：`seen` 去重依然要留着（防止近似检索撞车），但**不该靠加大 `k` 来兜底**。

## 6. ⭐ 实验：判断力到底是 prompt 的问题，还是模型的问题？

> **今天最有价值的一段。**

### 6.1 起因

搭好之后跑了一次，**10 轮全说"不够"**（`enough: false` ×10），
最后靠 `MAX_HOPS` 刹车停下。

按 10-08 §5.2 的教训，**不能直接下结论**。得先分清：

| 假设 | 怎么验证 |
|---|---|
| A. prompt 写得太严，模型其实判对了 | 换个更宽松的 prompt 试试 |
| B. prompt 没问题，是 `qwen2.5:3b` 判断力不够 | 换一个更强的模型，**证据一模一样** |

### 6.2 实验设计：控制变量

关键在 **"证据一模一样"**。所以先做一件容易被跳过的事：

> **把那次 10 轮跑出来的证据固定下来**（片段 `c500_0074` / `c500_0076` / `c500_0004`），
> 之后所有对比都喂这同一批文本。

这样两个模型看到的**输入完全相同**，唯一变的就是模型本身。
否则"A 说不够、B 说够"根本没法归因——可能是证据不同导致的。

### 6.3 结果

| 模型 | 同一批证据下 | 判断 |
|---|---|---|
| `qwen2.5:3b`（本地） | **10 次全部** `enough: false` | 稳定地判错 |
| DeepSeek（云端） | **第 1 轮**就 `enough: true` | 判对 |

而那个"28.4"**确实就在证据里**（`Attention Is All You Need` 第 7 页，
WMT 2014 英德 BLEU = 28.4）。

### 6.4 结论

> **这不是 prompt 的问题，是模型的判断力问题。**
> 证据已经够了，3b 的小模型**读不出来**。

**10 次全错**这一点很重要——它排除了"偶发抖动"。
如果是随机性，10 次里总该对几次。

### 6.5 为什么这个实验值得写

它体现的不是"我会调 prompt"，而是：

1. **遇到反直觉结果（10 轮全说不够），先怀疑自己**（prompt？阈值？）
2. **设计控制变量实验**把"我的实现问题"和"模型的固有能力上限"分开
3. **如实接受"换模型"这个结论**，而不是硬调 prompt 去凑一个能跑的结果

而结论本身也和 10-07 的计划对上了——那边就写了"本地 `qwen2.5:3b`
做判断和总结质量不够，Agent 阶段要换"。**今天用实验把这句话从猜测变成了证据。**

## 7. 长跑带出来的三条"语料级"发现

那次 10 轮的长跑虽然是"失败"的（模型判错才跑满），但**意外很有信息量**：

**① 答案其实第 1 轮就到位了。**
真正有用的那 3 条（含 28.4）第 1 轮就进了 `items`，
后面 9 轮全是白跑。**"多跳"没有带来越来越好的证据**。

**② 证据在爆炸，而不是在增长。**
最后 `items` 里堆了 27 条，里面大量是**参考文献列表、表格碎片、PDF 解析噪声**
（公式被拆成一行行符号之类）。

> 这正好踩中大模型已知的 **"lost in the middle"**：
> 上下文中间的信息最容易被忽略。证据越多，**有效信息反而越难被用上**。

**③ 整个 Agent 的价值，被"只有一篇论文"卡死了。**
见下面的反思，这条最重要。

## 8. ⭐ 关键反思：多跳**从来没有真正跑起来过**

把上面三条一归纳，得到一个必须正视的结论：

> **`qwen2.5:3b` 说"不够"的 10 轮里，检索并没有"跳到别的地方去"——
> 语料里根本就没有"别的地方"。**

只有一篇论文的库，任何问题相关的片段就在那几十个里。
`query` 怎么改写，捞出来的都是同一片区域。

**所以今天做出来的东西，严格说是**：

| 看起来 | 实际上是 |
|---|---|
| 一个会多跳的 Agent | 一个**只跑一轮**的 RAG（好模型会直接判够） |
| 有 query 改写 | 机制在，但**没有场景可以验证它** |

这不是 bug。这是 10-07 和 10-08 都写过的同一件事：

> **一篇论文撑不起多跳 Agent。**

今天只是第一次**用实跑把这句话坐实了**。
也就是说，**下一步必须加论文**，这不再是"计划的下一步"，而是"当前唯一的瓶颈"。

## 9. 今天的产出（可写进简历的点）

1. **`agent/engine.py`**：检索引擎的进程级缓存，
   多跳每一轮不再重建 BM25 索引和重排模型。
2. **出处标签机制**：`[论文名, p.页码]` 从检索结果一路传到最终答案，
   引用可追溯到片段级别（`chunk_id`）。
3. ⭐ **一次控制变量实验**：在**完全相同的证据**下对比
   `qwen2.5:3b` 与 DeepSeek，证明"判断力不足"是**模型能力**问题
   而非 prompt 工程问题（3b 模型 10/10 判错，且稳定）。
4. **量化了 `k=3n` 这种简陋补丁的失效边界**：
   当 `k` 超过 `HYBRID_CANDIDATE_K=20` 时，多跳退化为空转。

### 为什么第 3 条最值钱

它和 10-07 的重排选型、10-08 的复现性量化是**同一个能力**：

- 会**怀疑自己的实现**，而不是急着怪框架
- 会**设计对照实验**做归因
- 会**如实报告"这个方案不行"**
