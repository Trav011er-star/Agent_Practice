## 0. 起点：先把仓库收拾干净

开工前先还了三笔账，都是"不收拾就会一直绊脚"的：

| 事项 | 为什么 |
|---|---|
| venv 从 `paper-agent/venv` 挪到仓库根 `.venv` | 两个项目要共用一个环境，藏在 paper-agent 下面另一个项目够不着 |
| 目录名 `paper-Agent` → `paper-agent` | 统一小写 |
| 根 `.gitignore` 补 `.venv/` `venv/` `__pycache__/` | venv 以前靠 `paper-agent/.gitignore` 挡着，挪到根目录后**只剩根这份能挡它**（1.5G） |

### 0.1 ⚠️ venv 能搬，但有两处写死了绝对路径

`python.exe` 本身没问题——它靠**自己所在的位置** + `pyvenv.cfg` 反推环境根，搬到哪都能用。
真正坏掉的是另外两处：

```text
①  activate / activate.bat 里的 VIRTUAL_ENV   ← 写死旧路径
②  Scripts/*.exe 的外壳                       ← distlib 生成的启动器，exe 里嵌了绝对 python 路径
```

第 ② 条最阴：**`pip.exe` 双击一下什么输出都没有**，`uvicorn.exe` / `hf.exe` 退出码 1。
但 `python -m pip` / `python -m uvicorn` 一切正常——因为那条路根本不经过 exe 外壳。

**修法**：翻每个包的 `.dist-info/RECORD`，把所有 `*.exe` 对应的包找出来
（27 个包、33 个 exe），`pip install --force-reinstall --no-deps <pinned specs>` 重装一遍（70 秒）。

> ⭐ **判据：一个 venv 里，"能用"和"能搬"是两件事。**
> 判断标准不是"python 跑得起来吗"，是"**每一个 .exe 入口都还找得到自己的解释器吗**"。
> 顺带：重装后有 4 个 exe 依然是坏的，查下来**全是搬家之前就坏的**（`fastapi.exe` 需要
> `fastapi[standard]`；`httpx.exe` 在 GBK 控制台下遇到 emoji 自己崩了；`hf` 那个只是弃用提示）。
> **搬家会暴露旧 bug，但不会制造它们**——别把老问题算到搬家的账上。

### 0.2 ⚠️ Windows 改目录大小写：`git mv` 会直接拒绝

```bash
git mv paper-Agent paper-agent
# fatal: renaming 'paper-Agent' failed: Invalid argument
```

Windows 文件系统**不区分大小写**，git 认为"改前改后是同一个路径"。

**绕法**是两段式：

```bash
git mv paper-Agent paper-agent-tmp
git mv paper-agent-tmp paper-agent
```

> ⭐ 不绕的话，磁盘上文件夹看起来已经改了，但 **git 索引里还留着旧写法**，
> GitHub 上会永远显示 `paper-Agent`。**改完必须 `git status` 确认索引也跟着变了。**

## 1. research-agent 三件套

```text
research-agent/
├── settings.py    配置 + 跨项目导入的桥
├── tools.py       工具定义（今天一半的工作量在这）
└── main.py        Tool Calling 循环（20 行）
```

### 1.1 ⚠️ 为什么这个文件不能叫 `config.py`

一开始顺手想叫 `config.py`，撞了个真实存在的坑：**`sys.modules` 是按名字缓存的，不是按路径。**

```text
research-agent/config.py   ← 先被 import，注册为 "config"
paper-agent/agent/engine.py 里那句 `import config`
                           ← 拿到的是【上面那个】config，不是 paper-agent/config.py
                           ← AttributeError: module 'config' has no attribute 'collection_name_for'
```

**实测复现过。** 同理入口也不能叫 `agent.py`——会和 `paper-agent/agent/` 这个包撞名。

叫 `settings.py`，入口叫 `main.py`，两个雷都绕开。

> ⭐ **判据：Python 的模块名是全局单例，跨项目拼代码时它比路径更容易撞。**

### 1.2 ⚠️ `import settings` 那行的副作用不能删

`tools.py` 要 import 来自 paper-agent 的 `retrieve`，而那条路是靠
`settings.py` 里的 `sys.path.insert` 铺的。所以 `tools.py` 里必须先 `import settings`。

```python
import settings  # noqa: F401  （导入是为了副作用，不是为了用名字）
from agent.engine import retrieve  # noqa: E402
```

**踩过的现象**：从 `main.py` 跑一切正常（main 里先 import settings 了），
**单独跑 `tools.py` 就 `ModuleNotFoundError: No module named 'agent'`**。

> ⭐ 这就是 paper-agent §7.1「**加了个东西，但没接到该接的地方**」的翻版，
> 只不过这次接错的是"导入顺序"。**显式把依赖写出来，它才是真的。**

## 2. ⭐ `bind_tools` 到底做了什么

今天最大的认知修正。我一直以为它有点像"给模型装上了调用工具的能力"——**不是。**

它干的事，就是**往请求体里多塞一个字段**。实测把两次请求体打出来对比：

```python
llm._get_request_payload(msgs)                     # 不 bind
llm.bind_tools(ALL_TOOLS)._get_request_payload(msgs)  # bind 之后
```

`bind_tools(...)` 返回的是一个 `_ChatModelBinding`，身上挂着一个 kwarg：

```python
bound.kwargs.keys()   # ['tools']
```

而那个 `tools` 长这样——**这就是"工具"的全部真相**：

```json
[
  {
    "type": "function",
    "function": {
      "name": "query_corpus",
      "description": "在本地 LLM 论文库里做语义检索，返回最相关的原文片段，每条都带 [论文名, p.页码] 出处。\n\n什么时候用：…",
      "parameters": {
        "properties": { "question": { "type": "string" } },
        "required": ["question"],
        "type": "object"
      }
    }
  }
]
```

三件事：

1. **`description` 就是函数 docstring 的原文。** 一个字没改。
2. **模型看不到你的 Python 函数**，看不到 `retrieve`，看不到 Ollama，看不到向量库。
   它对 `query_corpus` 的全部认知就是上面这 9 行 JSON。
3. **没有"切换到工具模式"这回事**——只是多了一个可选的输出格式。
   API 相当于对模型说："你除了能写答案，**还能**写这样一段结构。"

> ⭐ **判据：调 Agent 的时候，你写的不是代码，是模型能看见的文字。**
> 函数体只有模型"决定调用"之后才会执行；**决定之前，它眼里只有那 9 行 JSON。**

## 3. 四步循环

```python
messages = [SystemMessage(SYSTEM_PROMPT), HumanMessage(question)]

for step in range(1, max_steps + 1):
    ai = llm_with_tools.invoke(messages)     # ① 发请求
    messages.append(ai)                      # ② 把模型的回复记进去
    if not ai.tool_calls:                    # ③ 出口：它不点单了
        return ai.content
    for call in ai.tool_calls:               # ④ 把每一单都执行掉
        result = TOOLS_BY_NAME[call["name"]].invoke(call["args"])
        messages.append(ToolMessage(content=result, tool_call_id=call["id"]))
```

### 3.1 ⚠️ ② 不能省，省了就变复读机

不把 `ai` 记进 `messages`，下一轮模型看到的上下文里就只有 `[用户问题]`——
**它压根不知道自己刚点过单**，于是原样再点一次。

> 这和 paper-agent §7.3 ② 那个 judge 复读是**同一个病**：
> 不是模型笨，是**你给它的上下文里缺了一块**。

### 3.2 ⚠️ `tool_call_id` 不是可选装饰

实测这次跑，**第 2 轮它一口气点了 3 单**：

```text
点了几单： 3
  → 调用 query_corpus 参数: {'question': 'BERT 和 GPT-3 的预训练目标有什么区别？'}
  → 调用 query_corpus 参数: {'question': 'BERT 的预训练目标是什么？…'}
  → 调用 query_corpus 参数: {'question': 'GPT-3 的预训练目标是什么？…'}
```

**同一个工具、三条结果回来。** 模型靠什么对上号？**靠 id，不靠顺序。**

漏了 `tool_call_id`，OpenAI 系 API 直接报：

```text
messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

### 3.3 ⚠️ 一个约束：几单就必须回几条，**不能在代码里"砍单"**

看到"一轮点 6 单很浪费"，第一反应可能是"那我只执行前 1 单"——**不行**，
API 硬要求每个 `tool_call` 都有对应的 `ToolMessage`。

所以想省检索，**只有两条路**：

- 在 **prompt 层**引导模型别重复（§6 用的就是这条）
- 或者在**工具内部**做去重 / 反馈

**代码层没有"少执行几单"这个选项。**

## 4. ⭐ 工具 docstring 是模型唯一能看到的说明书

### 4.1 边界实验：5 个问题，只有 1 个调了工具

只跑第 1 轮（不执行），看它调不调：

```text
【没调】法国的首都是哪里？        → 直接答：法国的首都是巴黎。
【没调】今天广州天气怎么样？      → 直接答：查不到…
【没调】用 Python 写一个快速排序  → 直接答：（写了一段代码）
【没调】BERT 是什么？             → 直接答：BERT（Bidirectional Encoder…）
【调了】BERT 和 GPT-3 的预训练目标有什么区别？  → 参数：{…}
```

**注意第 4 条**：「BERT 是什么」也是论文主题，它**没调**。
区别在 docstring 第二句划的那条线：

> 什么时候用：问题涉及这 5 篇论文的**方法、结构、实验数字、结论，或它们之间的对比**时。

- 「BERT 是什么」是常识定义，不在描述里 → 自己答
- 「BERT 和 GPT-3 的**区别**」命中"对比" → 去查

### 4.2 ⭐ 模型会**引用**你 docstring 里的话

问天气那条，它的原话是：

> 今天广州的天气我这边查不到——我没有联网或实时天气数据的能力，**只能访问一个本地 LLM 论文库**…

「只能访问一个本地 LLM 论文库」**就是 docstring 的原话**。

> ⭐ **判据：模型对"我有什么、我没有什么"的全部认知，来自你写给它的文字。**
> 不写清楚边界，它会在你问天气时也去翻论文库，然后拿一堆无关片段硬编。

### 4.3 写了四件事，第四件最容易被忽略

```python
@tool
def query_corpus(question: str) -> str:
    """在本地 LLM 论文库里做语义检索，返回最相关的原文片段，每条都带 [论文名, p.页码] 出处。

    什么时候用：问题涉及这 5 篇论文的方法、结构、实验数字、结论，或它们之间的对比时。
    什么时候不该用：闲聊、写代码、问时效性新闻，或论文库覆盖不到的主题 —— 直接回答即可，不要调用。

    参数 question 请填一个完整的自然语言问句（例如「BERT 和 GPT-3 的预训练目标有什么区别？」），
    不要只写几个关键词 —— 检索器是按语义匹配的，问句越完整，召回越准。
    """
```

| 句子 | 作用 |
|---|---|
| 第 1 句 | 干什么 + 返回什么样（顺带告诉它"结果自带出处，你可以引用"） |
| 第 2 句 | **什么时候调** |
| 第 3 句 | **什么时候不该调** ← 决定上面那 4 个"没调" |
| 第 4 句 | **参数怎么填** ← 最容易被忽略的一句 |

第 4 句的效果**直接可测**：第 1 轮它填进来的参数是完整问句
（`'BERT 和 GPT-3 的预训练目标有什么区别？'`），没有退化成 `BERT GPT-3 预训练目标` 这种关键词堆。

> ⭐ **判据：模型不知道你的检索器是语义匹配的。**
> 你不说，它就按"搜索引擎"的直觉塞关键词；你说了，它就给完整问句。
> **把工具的脾气写进 docstring，是调 Agent 的标准动作。**

## 5. `SystemMessage`：全局策略

第一版跑出来的答案很扎实，但**一条出处都没有**——因为**没有任何地方要求它引用**。

`SystemMessage`（`role='system'`）就是干这个的，**必须放在 `messages` 第一条**：

```python
SYSTEM_PROMPT = """你是一个论文问答助手，手上有一个本地论文库检索工具 query_corpus。

回答规则：
1. 涉及论文内容的问题，必须先用 query_corpus 检索原文，不许凭记忆作答。
   一个问题如果包含多个要点（比如要对比两篇论文），可以拆成几个针对性的子问题分别检索 ——
   这是允许的，也常常是必要的。
   但不要重复检索：如果某个内容上一次检索已经返回过，就不要换个说法再问一遍。
   与论文无关的问题（闲聊、写代码、时效性新闻）直接回答，不用调工具。
2. 答案里每一条来自检索的结论后面，都要标出处，格式 [论文名, p.页码]，
   且出处必须是工具返回里真实出现过的，不许自己编。
3. 工具返回的片段不够支撑回答时，直接说「论文库里没有找到相关内容」，不要硬凑。
4. 允许补充你自己的通用知识，但必须明确标注「（通用知识，非论文原文）」。
"""
```

### 5.1 分工：description 管工具，system prompt 管助手

| | 写在哪 | 管什么 |
|---|---|---|
| **工具 description** | 函数 docstring | **这一个工具**的边界：干什么、何时不该用、参数怎么填 |
| **System prompt** | `SystemMessage` | **整个助手**的行事准则：先查再答、必须引用、不许编 |

第 1 条里那句"与论文无关的问题直接回答"是个**交叉引用**，不是重新划边界。

> ⚠️ **别把工具的边界抄进 system prompt。** 抄两份，以后改一处忘一处，
> 就又是 §7.1 那个「加了个东西但没接到该接的地方」。

### 5.2 效果

出处从 0 到全篇 `[BERT (2018), p.2]`，而且第 4 条生效后，答案是**英文原文直接引用**，
不是转述——面试官随手翻原文就能对上。

## 6. ⭐⭐ 过度纠正实验：今天最值钱的一条

### 6.1 四版对照

| 版本 | 检索次数 | 结果 |
|---|---|---|
| 只有 docstring | 3 | 零出处，GPT-3 那块凭记忆硬编 |
| `+ system prompt`（初版） | 6 | 答案好了，但有 22% 重复 |
| 规则 1 改成「合并成**一句**问句」 | **1** | **崩了**：退化成"论文库里什么都没有" |
| 规则 1 改成「可拆，但别重复」 | **5** | ✅ 有分寸、有原文、有出处 |

### 6.2 ⚠️ 我先把一个"看着像问题"的数字当成了问题

看到 6 次检索，我先去量了重复率：

```text
第1次  3 条  新的 3
第2次  3 条  新的 3
第3次  3 条  新的 3
第4次  3 条  新的 3
第5次  3 条  新的 0   ← 和第 3 次一字不差
第6次  3 条  新的 2
────────────────────
合计 18 条，去重后 14 条
```

然后我下结论："22% 冗余，把 6 压到 1。"**这个结论是错的。**

正确的读法是：**6 次里只有 1 次纯浪费，另外 5 次都在挖新东西。**
证据是那版好答案引用的 `[BERT (2018), p.0] / p.1 / p.7` ——
**全都不在第 1 次查询能拿到的片段里**。是那些"子问题"把 BERT 的 MLM 原文挖出来的。

所以规则 1 改成"合并成一句"之后，**一次检索**只拿回来 GPT-3 的基准测试片段，
BERT 的 MLM 原文压根没进上下文 → 模型看不到 → 只好说"没有"。

> ⭐ **判据：看到一个数字（6 > 3）先别当问题，先问"它是不是在对症地干活"。**
> 讽刺的是我给这个建议就在同一轮对话里——我上一段刚说"给工具加 `lru_cache` 没用，
> 因为重复的是**语义**不是字符串"，下一段自己就犯了同一个错：
> **看了一个更浅的数字就动手。**

### 6.3 ⚠️ `lru_cache` 为什么救不了这个 case

看那两次"重复"的问句：

```text
第3次: 'GPT-3 的预训练目标是什么？自回归语言模型'
第5次: 'GPT-3 论文中描述的语言模型训练目标，最大似然估计，预测下一个词'
```

**两个字符串完全不同，`lru_cache` 一条都命中不了**，但它们检索出的结果一模一样。

> ⭐ **判据：别拿"字符串相等"当"重复"的判断标准。**
> 这里是语义重复，只有语义层的判断才拦得住——也就是**只能交给模型自己**。

### 6.4 正确的措辞：明确允许，只禁一件事

上一版被误读是因为写的是「一次就把各个要点合并成**一句**完整问句」——
它把"一次"执行成了"**只查一次**"。改成：

```text
   一个问题如果包含多个要点（比如要对比两篇论文），可以拆成几个针对性的子问题分别检索 ——
   这是允许的，也常常是必要的。
   但不要重复检索：如果某个内容上一次检索已经返回过，就不要换个说法再问一遍。
```

**把"可以"和"不可以"都写出来。** 只写禁令，模型不知道剩下的空间有多大。

### 6.5 最好那版的自发行为

第 2 轮它自己说：

> The first round didn't return the actual pretraining-objective passages.
> Let me search more specifically.

**它发现了上一轮没查到，并主动换了更精确的问法。** 检索次数落在 5 次（2 + 2 + 1）——
夹在 1 和 6 之间，第 3 轮只针对还有缺口的那一边（GPT-3）补了一枪，然后收手。

> ⭐ **判据：prompt 改动一次只改一处，然后看它有没有【过度遵守】。**
> 模型的默认失败模式不只是"不听"，**同样常见的是"听过头"**。

## 7. ⭐ 语料覆盖度诊断：库里到底有没有

四版跑下来模型都在说同一句话：**"GPT-3 论文里描述预训练目标的原文，库里没有。"**

这有两种可能，**结论完全不同**：

| 可能 | 含义 | 该怎么办 |
|---|---|---|
| 语料库里**真的没有** | **数据覆盖**问题 | 补语料 |
| 库里有，但**检索不到** | **召回**问题 | 调切分 / top-k / 重排 |

不能靠猜——直接翻库：

```text
库中 GPT-3 片段总数：749

autoregressive                命中  14 条   ← 含摘要 "we train GPT-3, an autoregressive language model…"
predict                       命中  33 条
unsupervised / self-supervised 命中  17 条
objective                     命中   8 条
likelihood                    命中   5 条
──────────────────────────────────────────
maximum likelihood            命中   0 条
predict the next token        命中   0 条
language modeling objective   命中   0 条
```

**结论：方向对，但过硬了。**

- GPT-3 论文**确实没把训练目标当重点讲**（重心在 in-context learning），
  那些"标准表述"真的一个字都没有 —— **不是检索坏了。**
- **但摘要里那句 `an autoregressive language model` 是能支撑结论的。**
  只是"只查一次"那版压根没拿到它。

最好的那版找到了**我都没找到的一条**：

```text
"GPT-3 also uses a single training objective which is not customized
 or designed for any task in particular"   [GPT-3 (2020), p.14]
```

我前面只搜了 `maximum likelihood` / `next token` 两条线，全落空就下了"库里没有"的结论；
它搜的是 `objective` 那条线（库里 8 条命中），挑中了最对的那条。

> ⭐ **判据：验证"库里有不有"时，关键词要撒网，不能只押一两个词。**
> 我押的那两个词全落空——**"没搜到"和"不存在"是两件事。**

## 8. ⭐ 一条张力：防幻觉的代价是假阴性

规则 3（"不够就说没有，不要硬凑"）是防幻觉的。但它过头以后：

```text
幻觉（false positive）    ：没查到，硬编一个          ← 规则 3 要防的就是这个
假阴性（false negative）  ：查到了弱证据，却说"什么都没有"   ← 规则 3 过头就变成这个
```

看两版措辞的差别：

| | 措辞 |
|---|---|
| **5 次那版** | 「论文库里能**直接支撑**的是 BERT vs GPT-1 的对比；关于 GPT-3 本身，检索到的片段**只提到**它不做梯度更新…**没有找到对训练目标的明确描述**」 |
| **1 次那版** | 「**论文库里没有找到相关内容**」 |

第一版区分了"有间接证据"和"有直接原文"，是**精确**的；
第二版把"证据不够详细"喊成了"什么都没有"，是**失真**的。

> ⭐ **判据：一个被严厉要求"不许编"的模型，会本能地往保守方向退。**
> **保守到失真，本身也是一种错误答案。**
> 这条张力（召回质量 ↔ 诚实度）值得记：**"我不确定"和"我不知道"是两个不同的档位**，
> prompt 里要给出**中间那一档**的说法，否则模型只有满格和零格两个选项。

## 9. 今天的产出

1. **`bind_tools` 的真身**：往请求体多塞一个 `tools` 字段（附实测 payload）。
   模型看不到你的函数，只看到 `name` / `description` / `parameters` 三样。

2. **四步 Tool Calling 循环**：invoke → append(ai) → 出口 → 执行 + `tool_call_id` 回填。
   实测模型**一轮就能并行点 3 单**，`tool_call_id` 是必需的。

3. **一份能划边界的工具 docstring**：5 个问题的实测边界（4 个不调 / 1 个调），
   以及"参数怎么填"那句对参数质量的实际影响。

4. **`SystemMessage` 全局策略**：4 条规则让答案从"零出处"变成"全篇原文引用"。

5. ⭐ **一条判据**：**`bind_tools` 不是给模型装能力，是给请求体加字段。**
   模型内部没有循环、没有记忆、没有裁判——"循环"在你的 Python 里，"记忆"在你的 `messages` 列表里。

6. ⭐ **一条判据**：**调 Agent，你写的是文字不是代码。**
   模型决策前眼里只有那 9 行 JSON；函数体只有它决定调用之后才执行。

7. ⭐ **一条判据**：**看到了数字先别当问题，先问"它是不是在对症地干活"。**
   6 次检索里 5 次在挖新信息，只有 1 次是浪费；把它压成 1 次，答案直接崩。

8. ⭐ **一条判据**：**prompt 改动一次只改一处，然后看它有没有【过度遵守】。**
   模型的默认失败模式不只是"不听"，**同样常见的是"听过头"**——
   规则 3 就从"防幻觉"滑成了"假阴性"。

9. ⭐ **一条判据**：**"我不确定"和"我不知道"是两个档位。**
   只给模型"必须诚实"这一个约束，它会退到"什么都没有"。
   **prompt 里要显式给出中间档的说法。**

10. ⭐ **一条判据**：**别拿"字符串相等"当"重复"的判断标准。**
    两次问句字面完全不同、检索结果一字不差——`lru_cache` 一条都拦不住。

11. ⭐ **一条判据**：**"没搜到"不等于"不存在"。**
    关键词要撒网；验证"库里有不有"时，一两个词落空说明不了什么。

### 为什么第 5~11 条最该讲

它们**不是关于代码的发现，是关于"边界在哪"的发现**：

| 条目 | 边界画在哪 |
|---|---|
| 5 | **模型的机制**和**我们组织的范式**的边界（范式归工程侧，不归模型） |
| 6 | **代码**和**给模型看的文字**的边界 |
| 7 | **一个数字**和**它是不是问题**的边界 |
| 8 | **"听过头"**和**"不听"**的边界 |
| 9 | **"不确定"**和**"不知道"**的边界 |
| 10 | **字面重复**和**语义重复**的边界 |
| 11 | **没搜到**和**不存在**的边界 |

第 7 和第 10 条尤其值得说：**我给出的判据，在同一轮对话里被我自己违反了。**
第 10 条我说完"别拿字符串当重复标准"，转头就看了个更浅的数字（6 > 3）动手改 prompt。
**知道判据和会用判据，是两件事。**
